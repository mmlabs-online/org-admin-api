FINDINGS
- Permission seeding precedent: ADM-006 migration (/home/user/org-admin-api/migrations/versions/20261117_c8a1f4e72d95_adm006_org_entitlements.py) inserts `admin:entitlements:read|write` into the admin app (id 00000000-0000-4000-8000-0000000000a1) with `is_admin=true`, granted to no role, `ON CONFLICT (app_id, key) DO NOTHING`. Downgrade deletes by key (role_permissions cascade). Other admin keys (users/orgs/apps/audit/roles) are seeded the same way. Only `admin:*` holders (super-admin) get new keys by default.
- Route-class test (/home/user/org-admin-api/tests/test_route_auth_classes.py): any new route fails `test_every_route_is_classified` and `test_bearer_route_permission_map` until it is added to the `BEARER` dict as (method, path): permission. It also checks the `x-permission` OpenAPI extension, 401 and 403 responses, the CORS matcher (admin CORS follows the BEARER map automatically) and the 401 sweeps. If the path has no placeholders, nothing is needed in `_fill`.
- Single-document precedent: `/me/permissions` (me_router.py) sets `Cache-Control: no-store` via an injected `Response`. It is a SELF_SCOPED entry, which does not apply here: stats is a normal BEARER route with one permission.
- Audit actions exist: `AUTH_LOGIN_SUCCEEDED = "auth.login_succeeded"` and `AUTH_LOGIN_FAILED = "auth.login_failed"` (app/modules/audit/actions.py). Index `ix_audit_log_action (action, occurred_at, id)` exists, so `WHERE action = X AND occurred_at >= now() - interval '24 hours'` is an index range scan. A count per action meets the bounded-cost criterion.
- `users` has only a `status` CHECK constraint (active/disabled) and no visible index on `status`, `created_at` or `email_verified_at`. Table scans over users and orgs are acceptable at current scale but are not "indexed". The criterion's "indexed only" wording is a stretch for these tables; see Risks.
- `role_assignments` has `expires_at`, nullable `org_id`, and indexes on `role_id` and `org_id`. Assignments link to an app through `roles.app_id`, so member counts need a join through `roles`.

RECOMMENDATIONS
1. Path (AC "single document", R9): `GET /api/v1/stats/dashboard`, or `GET /api/v1/dashboard-stats`. Both break the strict `/api/v1/<plural-noun>` pattern, so either way it is an R9 exception. I prefer `/api/v1/stats` (a noun, a single document) because it can later gain sibling documents without a new exception. Exception wording for R9 and a new decision D26 in identity-architecture.md: "`GET /api/v1/stats` (singular document, not `Page[T]`; D26)". Also add it to the R3 class 1 list as an ordinary Bearer admin endpoint (no self-scoped carve-out, no ADR-0008 amendment needed).
2. Response shape (snake_case, ISO 8601 UTC timestamps, additive-only afterwards):
   `{generated_at, users:{total, by_status:{active, disabled}, unverified}, organizations:{total, by_status:{active, suspended}}, apps:{total, by_status:{...}}, sign_ins_24h:{window_start, window_end, succeeded, failed}, sign_ups_by_month:[{month:"2026-11", count}], members_per_app:[{app_key, member_count}]}`.
   - Always emit all known status keys with 0 filled in. Do not omit zero keys, or the UI has to guess.
   - `sign_ups_by_month` is exactly 12 entries, oldest first, zero-filled, with month in `Asia/Ho_Chi_Minh` (`date_trunc('month', created_at AT TIME ZONE 'Asia/Ho_Chi_Minh')`). Include the current partial month and document that it is partial. Put `time_zone: "Asia/Ho_Chi_Minh"` in the document so the choice is self-describing.
   - `members_per_app` is ordered by app key. It should include apps with 0 members and should not hide disabled apps (the apps status breakdown already shows them).
   - Document the caveats from spec §5.9 in the OpenAPI description (failed sign-ins include unknown emails; 429 and Turnstile refusals are not counted; sign-ups include CLI-created accounts).
3. Permission seeding (OQ4 `admin:stats:read`): new migration, expand-only, same pattern as ADM-006 (`is_admin=true`, granted to no role, `ON CONFLICT DO NOTHING`, downgrade deletes the key). Reason: the `is_admin` flag makes the guard in `rbac/service` require `admin:*` to grant it, which keeps a privilege boundary consistent with the other admin keys. The owner's wording "counts only" does not change that; `is_admin=false` would let any role manager hand it out to non-admin-app roles. Check `tests/test_rbac_schema.py` / `tests/test_rbac_migrations.py` for hard-coded permission lists and update them. Staff roles need it assigned by a super-admin; flag that to the owner so the dashboard does not 403 for staff by surprise.
4. Per-row access: the endpoint needs only `admin:stats:read` and returns counts across users/orgs/apps, so staff with stats but no `admin:users:read` can see aggregate counts. That matches the owner's answer; note it in the docs. Add `x-permission` via `require_permission("admin:stats:read")` as usual.
5. Cache-Control: `no-store`, as `/me/permissions` does (via `response: Response`). Matches the AC. Do not add ETag or max-age in v1. If load ever matters, add a short `private, max-age` later (it is additive). Make sure the 401/403 error responses are not cached either; check whether the shared error handler sets it, since AC only requires the 200.
6. Auth class and read-only: no audit row. Test with a count of `audit_log` rows before and after, so a future change cannot silently add one (R4 covers mutations only).
7. ADM-016 `member_count` must share the definition. Put one function in the repository layer (for example `count_members_by_app(app_ids=None)`) that both ADM-015 and ADM-016 call. Query: `SELECT r.app_id, count(DISTINCT ra.user_id) FROM role_assignments ra JOIN roles r ON r.id = ra.role_id JOIN users u ON u.id = ra.user_id WHERE (ra.expires_at IS NULL OR ra.expires_at > now()) AND u.status = 'active' GROUP BY r.app_id`. Be sure the count is DISTINCT users across app scope and all orgs (not per org). Include no email-verified filter (per OQ5). The `admin` app counts staff the same way. Put it in the shared module (the rbac repository or a small `members` helper) and have ADM-016 import it so the two numbers cannot drift. Add a test in ADM-015 asserting the stats `members_per_app` equals the ADM-016 `member_count` for the same data, once ADM-016 lands; until then, test the function directly. Lean on `ix_role_assignments_role_id`; the plan should use EXPLAIN on realistic data.

RISKS
- "Indexed queries only" for users/organizations/apps is not literally achievable without new indexes: group-by counts on small tables use seq scans. Either interpret the criterion as "no audit_log scan outside the indexed range" (my recommendation, since the audit table is the one that grows) or add indexes on `users.created_at` and `users.email_verified_at` (probably not worth it). The planner should word the AC precisely; p95 < 200 ms (§6) is the real target.
- Time-based audit counts use `occurred_at` against `now()`; failed logins that fail in a rolled-back transaction might not write audit rows (ADM-004b's design handles it, but confirm in the test that `login_failed` rows are actually committed in the test harness).
- The 12-month sign-up series over `users.created_at` is a full scan of users; fine now, revisit if users reach hundreds of thousands (then add `created_at` index).
- The new permission is granted to no role, so the dashboard returns 403 for everyone except super-admin until roles are updated; the admin-pan team needs to know.
- Naming the path `/stats` exposes a general namespace; if the owner later wants other reports (OQ9 and following), reuse `/api/v1/stats/...` or `/api/v1/reports/...` consistently rather than inventing a second pattern.
- Admin CORS applies automatically through the BEARER map, but only non-credentialed; no work needed, just run test_admin_cors.
