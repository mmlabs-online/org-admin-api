## Security review: USR-10 (staff session list, revoke one, revoke all)

I read `git diff origin/main...HEAD` plus the code around it: `admin_auth/deps.py`, `audit/service.py`, `audit/context.py`, `users/repository.py`, the login path in `auth/service.py`, `users/service.py::set_status` and `auth/password_reset.py`. As you asked, I did not run `make check` or pytest.

**Verdict: PASS, with no blockers.** There are no 🔴 or 🟡 findings, only notes.

### What I checked
- **Authz per route.** All three routes use `**require_permission("admin:*")` (`app/modules/users/router.py:76-80`), on top of the router-level `current_admin`. `tests/test_route_auth_classes.py:81-83` pins all three routes to `admin:*`, and `test_routes_require_admin_wildcard` confirms that holding `admin:users:read` and `admin:users:write` gets 403 `permission_denied`, with no audit row and no revoke. `require_permission` returns a fresh `dict(_ERROR_RESPONSES)`, so adding the 404 entry at `router.py:78` does not change other routes.
- **IDOR on `session_id`.** The update matches on `id`, `user_id` and `revoked_at IS NULL` together (`app/modules/sessions/repository.py:153-166`). If no row matches, it returns 404 `Session not found`. That covers a session of another user, an unknown id and an already-revoked id alike, so the response does not reveal whether a session id exists. The test `test_revoke_one_other_users_session_404` covers this.
- **Self-guard and denied audit.** In `app/modules/sessions/staff_service.py:71-87`, both revokes lock the user row, then run the self check and the G5 check inside `except DENIED_ERRORS`, then call `record_denied` with the target user and the reason only. The UUID is copied before the rollback can expire the ORM object (line 76). `SelfSessionChangeForbiddenError` is added to `DENIED_ERRORS` (`app/core/errors.py:93`). The list route also returns 403 for self, and as a read it writes no row (ADR-0009 §8). The tests `test_session_self_revoke_writes_denied_row` and `test_service_privileged_target_requires_wildcard` cover this.
- **Lock order and deadlock.** The order is: user row `FOR NO KEY UPDATE`, then an `UPDATE` on `account_sessions`. That matches password reset (`password_reset.py:104-110`). `set_status` takes the admin-app lock, then the user row, then sessions, so its user-before-sessions order is the same. Login takes the user row `FOR SHARE` before touching device and account rows, which is also consistent, and it simply waits for the user lock. Cookie logout updates `account_sessions` by device without a user lock. It can share at most one row with a revoke-all of one user, assuming there is one account session per (user, device), so no lock cycle can form. Audit inserts take only `KEY SHARE`, which this lock mode does not block. I found no deadlock path.
- **No secrets in responses.** `UserSessionRead` (`app/modules/sessions/schemas.py`) is an explicit allow-list: `id`, `created_at`, `last_used_at`, `device_last_seen_at`, `ip`, `user_agent`. It contains no token, hash or `device_session_id`, and `test_list_item_has_exact_keys` pins it. The revoke routes return 204 with an empty body.
- **IP and user agent kept out of audit and logs.** The audit `changes` hold only `account_session_ids` (capped at 100) and `account_sessions_revoked`. The service never logs IP or user agent. `test_revoke_audit_changes_exact_keys` covers this.
- **Cache-Control.** The list route sets `no-store` (`router.py:107`).
- **Shared device.** The revokes touch `account_sessions` only and filter by `user_id`, and device sessions are never updated. `test_revoke_all_shared_device_keeps_other_user` covers this.
- **Effect on `/auth/token`.** After either revoke it returns 401 `session_invalid`; both are tested.
- **Docs.** `docs/deploy.md:253-258`, the OpenAPI description, `docs/identity-architecture.md` and `docs/spec-v1.md` §5.10 all state correctly that tokens already issued, admin tokens included, stay valid until `exp`. That is at most `ACCESS_TOKEN_TTL_SECONDS` (43200 s in production per `deploy.md:224`) plus the 30 s leeway, which matches `app/core/access_token.py:29`. The docs also say a revoke does not block a new password sign-in. The runbook correctly says session revoke is not a response to a compromised account and points to: disable or revoke admin roles, hold that for TTL + 60 s, reset the password before re-enabling, and use emergency key rotation for an immediate global cut. The compromised-staff bullet now lists staff session revoke among the actions that do not end an issued admin token. All of this is consistent.

### Findings
- 💭 **G5 check without the admin-app lock** (`app/modules/sessions/staff_service.py:80-81`, and `:53` for list). `user_has_privileged_assignment` runs without `lock_app("admin")`, whereas `set_status` takes that lock (`users/service.py:47`). A role grant committed at the same moment could make the check stale. It cannot be exploited today because all three routes already require `admin:*`, so `require_super` always passes. If the route permission is ever lowered, take `lock_app(ADMIN_APP_KEY)` before `get_for_update`, in the same order as `set_status`.
- 💭 **Audit rows carry the staff caller's IP and user agent.** `AuditContextDep` (`app/modules/audit/context.py:12-13`) stores the actor's request IP and user agent in the audit row's context columns, as every admin audit row already does. The target's device IP and user agent never appear, which is what the AC requires. No change needed; I mention it only so nobody reads "no IP in audit" as covering the actor's own request context.
- 💭 **Revoke-one accepts a stale session** (`app/modules/sessions/repository.py:153-166`). It also succeeds (204 plus an audit row) on a session that is unrevoked but already idle- or max-age-expired, even though the list hides it. This is harmless because that session cannot mint tokens anyway, but if exact list/revoke symmetry matters, add the same idle and max-age predicates or document the difference.
- 💭 **Duplicate repository method** (`app/modules/sessions/repository.py:166`). `revoke_all_accounts_of_user_ids` repeats `revoke_all_accounts_of_user` with `RETURNING` added. A follow-up could make the original return the ids and drop the duplicate (R7: do not do it in this diff).
