### Deviations from plan
- **`verify` order:** the plan consumes first and relies on rollback when the user is disabled. Implemented as: find the token's user → lock the user `FOR UPDATE` → disabled/missing → 422 → then the atomic consume. Same outcomes and still race-free single use, but the token stays unused for a disabled user without depending on a rollback (the non-strict test client does not roll back on error).
- `verification_message(link)` takes only the link (the plan's `to` argument would be unused).
- `X-MM-App` on resend is checked before the cookie (dependency order like `/token`), so a request without the header gets 403 even without a cookie.
- `prepare` normalizes the email inline (`strip().lower()`, same as `auth.service.normalize_email`) to avoid an import cycle `auth.service → hooks → email_verification → auth.service`.
- Extra tests beyond the plan list: `test_unexpected_error_does_not_kill_worker`, `test_resend_forwards_rotated_cookie` (split out of `test_resend_ok_202`), `test_resend_disabled_user_401`, `test_resend_validation_422`, `test_build_email_sender`, `test_disabled_sender_logs_without_address`, `test_smtp_optional_locally`, `test_email_link_base_url_loopback_only_locally`. Tests that check logs re-enable the module logger, as `test_auth_cors.py` does (Alembic's `fileConfig` in the session fixture disables loggers that already exist).
- Size: production code + migration ≈ +946 / −18 lines (plan estimate 650–750); tests +1249, docs +167.
