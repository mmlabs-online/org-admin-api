## ADM-013 consult (api-platform-engineer, read-only)

### Findings (current state, verified in code)

1. **No shared error model exists.** `app/modules/auth/router.py:65` has `_ERR = {"description": "Error envelope"}`, which has no `model`, so the schema is not in the document. `app/modules/admin_auth/deps.py:30` `_ERROR_RESPONSES` (401/403) has the same problem. It is injected by `require_permission()` at line 107. The `_with_409(...)` helpers in `rbac/router.py` and the `_WRITE`/`_REVOKE` dicts in `users/router.py:47` and `rbac/assignments_router.py:59` add a description-only 409. `jwks_router.py:21` and `catalog_router.py:24` have their own `responses=` blocks. Organizations, audit and users only get errors through `require_permission`.
2. **422 handling.** FastAPI auto-adds `422 -> HTTPValidationError` (plus `ValidationError`, `ValidationError.loc`) to every operation that has params or a body, unless the route already declares 422. Only some auth routes declare 422 today (as description-only, which suppresses the default there). All admin routes (they have path, query or body params) still show the default. So a global fix is required; per-route fixes will not cover all of them.
3. **`origin` required: root cause found.**
   - `get_app_context` (`app/modules/auth/deps.py:71`) declares `origin` as optional and already does the 403 check.
   - `get_link_origin` (deps.py:100) declares `origin: Annotated[str, Header()]`, which is required. It is used by `forgot_password`, `resend_verification`, and the signup hook (`get_signup_hook`).
   - The required declaration is what leaks into OpenAPI. Check whether signup also shows it. The ticket only names forgot and resend, but signup likely has the same problem via `get_signup_hook`.
   - Runtime behaviour: `MailLinkAppContextDep` is a sub-dependency solved before `get_link_origin`. A missing Origin therefore raises the 403 `AppError` first and never becomes a 422.
4. **Request ID.** `RequestIdMiddleware` already sets `scope["state"]["request_id"]` (so `request.state.request_id` works in handlers) and appends `X-Request-ID` to every response, preflights included. It is a server-generated UUID4. There is no OpenAPI mention of the header.
5. **`operation_id`.** None is set anywhere; no `generate_unique_id_function`. The current ids are FastAPI's `<fn>_<path>_<method>`, so they change if a function or path is renamed. All routers are `include_router`-ed in `create_app` (main.py:101-107).
6. **500s.** There is no handler for bare `Exception`. Unhandled errors go through Starlette's `ServerErrorMiddleware` and return plain text, not an envelope. Do NOT document 500 as `ErrorEnvelope` unless you add a handler, because the document must match what the server returns. Recommend leaving 500 undocumented or giving it an explicit follow-up. If AC1 is read as requiring 5xx, add a catch-all handler and flag it to the planner (it is a behaviour change and arguably out of scope under R7).
7. **Offline dump feasibility.** `create_app()` with default `Settings` (local env, loopback DSN) needs no secrets; the JWT key is ephemeral and the engine is lazy. `app.openapi()` works even when `openapi_url=None`. `app/cli.py` is a hand-rolled dispatcher in `amain()` (no argparse subcommand tree); `_Parser`, EXIT_* and the "never print raw errors" convention are in use. There are no existing OpenAPI snapshot tests; `tests/test_route_auth_classes.py` and `tests/test_device_cookie.py` already assert on `app.openapi()` (bearer scheme, `x-permission`, device cookie scheme), so the post-processing must not disturb those.

### Recommendations

**A. ErrorEnvelope model (AC1, AC2; R6)**
- Add in `app/core/errors.py`: `ErrorBody(BaseModel)` with `code: str`, `message: str`, `details: Any | None = None`, and `ErrorEnvelope(BaseModel)` with `error: ErrorBody`. Use these models in `_envelope()` or a test so the doc and the runtime cannot drift.
- Export `ERROR_RESPONSES: dict[int, dict]` with `{"model": ErrorEnvelope, "description": ...}` for 400/401/403/404/409/422/429, so routers share one source of truth. For 401/403/409 keep per-route descriptions by merging (`{**ERR, "description": "..."}`).
- Do NOT rely on touching every route by hand. Add one global pass, which is robust against future routers and satisfies "across all routers, admin included":
  - Subclass `FastAPI`, or wrap `app.openapi`, so `create_app` installs a `custom_openapi` that caches `app.openapi_schema`. Walk `paths.*.<method>.responses`.
  - For every 4xx/5xx entry, set `content: {"application/json": {"schema": {"$ref": "#/components/schemas/ErrorEnvelope"}}}` and add the `ErrorEnvelope`/`ErrorBody` components.
  - Delete `components.schemas.HTTPValidationError`, `ValidationError`, and any `ValidationError.loc` variants. Replace every `422` response with a `ErrorEnvelope` one with a `validation_error` description.
  - Guarantee: add a test that asserts no `$ref` ends in `HTTPValidationError` or `ValidationError` anywhere.
- Alternative (the cleaner pattern if you prefer to avoid post-processing): set `responses={422: ERR_422}` on the top-level `FastAPI(responses=...)` / `app.include_router(..., responses=...)`. This is the lower-risk route and keeps FastAPI generating the schemas. But note include-level `responses` are merged into every route, including 401/403 on public routes (wrong: public routes would get a documented 401). Use the global `{422}` only (every route with inputs returns 422, and routes without params, such as health, would get a spurious 422). So post-processing in `openapi()` is the better fit for "only where a 422 exists": keep FastAPI's auto-422 (it appears exactly on the routes that can return it), then rewrite its schema ref to `ErrorEnvelope`. That removes the need to declare 422 per route.
- Implementation hint for the rewrite: FastAPI emits the 422 content as `$ref HTTPValidationError`; replace that ref string, then drop the two schemas from `components.schemas`.
- Keep 429 `Retry-After` header documentation (`headers: {Retry-After: {schema: {type: integer}}}`) on rate-limited routes if cheap; the server does send it (`RateLimitedError`). Optional.
- 401 on Bearer routes also returns `WWW-Authenticate`. Could be documented in the same pass; optional.
- 204/202/304 handling: `_http_exception_handler` returns an empty body for 204/304. Do not attach an envelope to those (they are not 4xx anyway).
- `details` typing: it is `Any` today (a list for 422, a dict for others, null otherwise). Document it as `{}`/anyOf (nullable) and say so in the description. Do not tighten it; tightening breaks clients under R9. Optionally add per-code documentation in the description of known `code` values (validation_error, not_found, ...).

**B. Stable `operation_id` (follow-up F3)**
- Pass `generate_unique_id_function` to `FastAPI(...)` (or each `APIRouter`) producing `f"{route.tags[0]}_{route.name}"`-style ids, or simpler, use `route.name` and have a test assert uniqueness (FastAPI warns on duplicates). Prefer `<name>` alone if function names are unique; otherwise `tag_name`. Note this CHANGES generated operationIds. Since the document has not been published as a contract (admin-pan hand-writes types), this is safe, but record it in the plan and the changelog.
- Add a test: every operation has an `operationId`, ids are unique, and (a snapshot-style assertion) match `^[a-z][a-z0-9_]*$`. Also pin that no id contains the path (that is the instability source).
- Do not set `operation_id=` by hand on each route unless ids must be curated; the function is lower-touch.
- Rename caution: it is the function name that becomes the id, so a lint note "renaming a route function is a client-visible change" belongs in docs.

**C. Remove `origin` from the documented params (AC3)**
- In `get_link_origin`, change the signature to take no `Header()` at all: reuse the already-validated `App` context and re-read the header via `Request` (`request.headers.get("origin")`), or accept `origin: Annotated[str | None, Header()] = None` and raise `OriginNotAllowedError("Origin is not allowed")` when None (unreachable in practice, but keeps mypy --strict happy and fails closed). This keeps the optional, already-existing declaration from `get_app_context`.
- Then also remove it from the documented params entirely, because browsers send `Origin` themselves and clients should not model it. Do that in the post-processing: drop parameters with `in: header` and `name` in `{origin}` (case-insensitive) from every operation. Keep `X-MM-App` documented (clients must set it, R11) and make sure it is not marked required in a way that changes the 403 behaviour (it is already optional, and the server answers 403, so documenting it as optional with a description "required for cookie routes; 403 if missing" is accurate; or mark required in the doc only if you are willing to decide that; if so, say it in the plan).
- Keep the server check. Tests: the existing tests that send a missing or unregistered Origin and expect 403 are the proof (AC3 says "the existing tests prove that"). Run them unchanged. Verify the order guarantee in the router docstring (line 315) still holds.
- Check signup and other cookie routes for the same `origin` leakage in the generated doc and strip globally.

**D. Offline deterministic dump (AC4)**
- Add a `openapi` command to `app/cli.py` dispatch in `amain()` before the grant-super-admin fallthrough (`if argv[:1] == ["openapi"]`). It must not call `_load_settings`/`get_settings` (that reads `.env` and env, and would fail in CI shells); build `Settings(_env_file=None, app_env="local", ...)` explicitly (init kwargs win over env), and call `create_app(settings)`. Alternatively `create_app()` under a controlled env; explicit Settings is more reliable. This needs no DB (engine is lazy, no lifespan is run).
- Imports must stay lazy inside the function (the module docstring says CLI never imports `app.main` at import time).
- Output: `json.dumps(schema, indent=2, sort_keys=True, ensure_ascii=False) + "\n"`, with an optional `--output <path>` (default stdout) and write bytes as UTF-8 with `\n` newlines. `sort_keys=True` makes determinism independent of dict insertion order (route order in `app.routes` is also deterministic, but do not rely on it). Do not include timestamps or version drift; `version="0.1.0"` is fixed, so fine.
- Error handling: follow the CLI convention (fixed message, no traceback), a usage constant `OPENAPI_USAGE`, exit codes EXIT_OK/EXIT_USAGE/EXIT_FAILURE.
- Makefile: add `openapi` to `.PHONY` and `openapi:  ## Write the OpenAPI document: make openapi [OUT=openapi.json]` that runs `uv run python -m app.cli openapi $(if $(OUT),--output $(OUT))`. Decide the default: either stdout, or a committed `docs/openapi.json` snapshot. A committed snapshot plus a test comparing it is the strongest drift guard but adds a file that needs regenerating on every API change; offer it as an option for the planner (I would propose: do not commit in this ticket, test determinism only, and let admin-pan consume the output, unless the owner wants the snapshot; ask).
- Determinism test: call the dump function twice in-process on two separately created apps and assert byte equality; also run via subprocess once with a scrubbed env (`DATABASE_URL`/secrets unset) to prove "no database or secrets". Test that `create_app().openapi()` is not cached across calls in a way that hides nondeterminism (compare two fresh apps).
- Production safety: `API_DOCS_ENABLED` is irrelevant to the dump (`app.openapi()` works when `openapi_url=None`); mention that in the docs.

**E. X-Request-ID (AC6, optional): cheap and non-breaking, recommend doing both parts, in different amounts**
- Header documentation: add `X-Request-ID: {schema: {type: string, format: uuid}, description: "Server-generated id of the request; quote it to support"}` to every response in the same global post-processing pass (all status codes, including 2xx and the ErrorEnvelope ones). Pure doc change, matches `RequestIdMiddleware` (all responses carry it, including preflights). Under R9 this is additive and safe.
- Envelope field: adding `request_id` to the error object is additive (new optional response field is safe per the compatibility table). Place it inside `error` (`{"error": {"code","message","details","request_id"}}`), not at the top level, to keep one nesting. But note: (a) R6 in CLAUDE.md spells the shape as `{code, message, details}`, so this needs the owner's/spec's sign-off and an R6 text update; (b) many tests compare the body exactly (about 21 occurrences of `== {"error": ...}` across 11 files, e.g. `tests/test_errors.py`), so they would need updating or the field would break equality assertions; (c) clients that generate strict types from `required` lists are unaffected if the field is not in `required`; declare it `request_id: str | None`, not required. Handlers get it via `request.state.request_id` (the middleware sets `scope["state"]`; `Request.state` reads that), with a `getattr` fallback to None for responses produced outside the middleware (there are none, since it is outermost, but keep it safe).
- My recommendation: do the header documentation now (zero risk, no test churn). Defer the envelope field to the owner decision or a follow-up, because it needs an R6 amendment and touches the exact-equality tests. If the planner includes it, the decision to record is: field inside `error`, optional/nullable, never client-supplied (already true since inbound ids are ignored), and cover it by a test that the body id equals the `X-Request-ID` header.

### Risks

- **Breaking generated clients**: changing `operationId`s changes generated function names in admin-pan. Pre-contract, so acceptable, but call it out in the plan and notify the owner.
- **Global post-processing hiding mistakes**: a pure rewrite can mask routes that do not actually return the envelope. Mitigate with tests that hit one real 401, 403, 404, 409, 422, 429 and compare the JSON to the `ErrorEnvelope` schema (validate with `ErrorEnvelope.model_validate`).
- **Caching**: `FastAPI.openapi()` caches in `app.openapi_schema`; post-process inside the override once, and never mutate shared dicts (FastAPI's `responses` dicts such as `_ERR` and `_ERROR_RESPONSES` are module-level and mutated by `_with_409` patterns, `_WRITE["responses"][409] = ...`). Mutating them in place could leak across `create_app()` calls and break determinism tests. Deep-copy before editing.
- **Dropping `origin` from the doc can reintroduce a required parameter** if any other dependency uses `Header()` without a default; add a schema test that asserts no operation has a required header parameter named `origin` (case-insensitive), and ideally none at all except where intended.
- **500 documentation mismatch** (finding 6): documenting 5xx with the envelope would be false today.
- **Exact-body test churn** if `request_id` is added to the envelope (finding E).
- **`sort_keys` and JSON Schema key order**: sorting changes the readability of the snapshot versus FastAPI's natural order (`openapi`, `info`, `paths`...). Harmless, but mention in the docs.
- **Mypy strict**: the `openapi` override typing (`dict[str, Any]`) and the `FastAPI` subclass or monkeypatch (`app.openapi = custom`) need a `# type: ignore[method-assign]` or a subclass to pass `make check`.
