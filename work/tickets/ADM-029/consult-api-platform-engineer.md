FINDINGS
1. DB constraints already exist (ADM-028): handled_iff_done and handler_only_when_done. The AC "DB constraint keeps status and handler fields consistent" is already met for status vs handled_at. Gap: nothing forces handled_by NOT NULL when done. This is deliberate, because handled_by is FK ON DELETE SET NULL, so a deleted staff user would otherwise break it. Do not tighten it. The service sets all three together (status, handled_by, handled_at). Optionally add a CHECK that resolution_note is allowed only... no, do not; a note is allowed on an open report, e.g. before reopening.
2. The bug_reports module only has auth_router.py (cookie class, /auth/bug-reports). Staff endpoints need a separate admin router (router.py), mounted under /api/v1 with current_admin and require_permission, exactly like stats/router.py. Do not mix the two auth classes in one router (R3, tests/test_route_auth_classes.py).
3. updated_at: TimestampMixin exists, so version_etag(updated_at) works as in organizations/entitlements/rbac. Check that updated_at has onupdate or a DB trigger. Without it, the ETag will not change on PATCH. Verify, and set it explicitly in the service if needed. A no-op PATCH must not bump updated_at (otherwise the ETag changes with no audit row).
4. app_version is validated as printable ASCII, 1..64 (can contain < > & " '). page_url is http/https, stored reduced (https://host[:port]/path; the CHECK regex only excludes ?#@ and whitespace, so the path can contain < > " '). user_agent is printable (up to 512). description and resolution_note are free text. All are untrusted.

RECOMMENDATIONS
Contract
- Routes: GET /api/v1/bug-reports (Page[BugReportListItem]), GET /api/v1/bug-reports/{id}, PATCH /api/v1/bug-reports/{id}. Plural noun, UUID id, so R9 is satisfied and no exception is needed.
- Permissions: seed admin:bug-reports:read / admin:bug-reports:write in a migration with a working downgrade (R2; this is a High path, so it needs Ming's approval). Mirror the previous permission seed (e.g. the entitlements migration 20261117_c8a1f4e72d95). Update the BEARER map in tests/test_route_auth_classes.py and add x-permission via require_permission(...). If the migration inserts permissions, also check the tests that count or enumerate the permission catalog.
- Cache-Control: no-store on list, detail AND the PATCH response (all carry reporter email). Set it on the 412 and 404 paths too if cheap; at minimum on 2xx.
- Detail also gets an ETag (version_etag(updated_at)) and ETAG_RESPONSE_HEADER in OpenAPI. List has no ETag (precedent: check what entitlements list does; keep it consistent). PATCH uses parse_if_match, raises the existing 412 precondition_failed error carrying the current ETag. Do the If-Match check under SELECT ... FOR UPDATE so that concurrent PATCHes are serialized and the check-then-write is atomic. Follow the entitlements service pattern.
- List filters: app (key, by `app_key` query param, consistent with the app-key addressing of D18; unknown key gives an empty page or 404? Recommend 422/404 is wrong for a filter; return an empty page, or 404 only if existing list endpoints do it — match precedent), status (enum open|done, else 422), reporter (user id UUID; do not offer email search in v1, it would put PII in query strings and logs), created_from / created_to (timestamptz, inclusive from, exclusive to; 422 if from > to). limit <= 100, offset (PageDep). Stable sort: created_at DESC, id DESC (matches ix_bug_reports_created_at_id, which is ascending but is scannable backward). Offer no free-form sort parameter in v1. Need an index for the status-only filter without app (status, created_at, id) only if volume warrants; skip it for now but note it. Page[T] total is needed, so count query is a second query; fine at this size.
- Response shapes: list item = id, app_key (+ app name), status, reporter {id, display_name} (email only in detail, which reduces PII in bulk lists; ticket says reporter email is PII, so I recommend list shows only id and display name, or says so explicitly), description_excerpt? Avoid truncation logic in v1: either include full description in the list (5000 chars x 100 is 500 KB worst case) or add a fixed 200-char excerpt. Recommend the excerpt as a plain-text field `description_preview`, never HTML. Detail adds full description, org {id,name}, page_url, app_version, user_agent, resolution_note, handled_by {id, display_name}, handled_at, created_at, updated_at, attachments: [] (always present array, so ADM-030 is additive and not breaking).
- Joins: the user might be deleted or the org nulled (SET NULL), so reporter fields should come from a LEFT JOIN or users with RESTRICT (user_id is RESTRICT, so reporter is always present). org and handler are nullable; document as nullable.
- PATCH body: extra="forbid", all fields optional, at least one required (422 on empty body). status: enum open|done (422 for others, free via the enum). resolution_note: str | None, 1..5000 chars after the same clean as description (text.clean_description or similar), null or "" clears? The DB CHECK forbids empty strings, so make null the clear value and 422 on "" (or normalize blank to null; pick one and test it). Use model_fields_set to distinguish "absent" from "null". Status transitions: done on done = no-op (no write, no audit, no handler change, handled_at not refreshed); open on open = no-op. Do not let a PATCH change handler/handled_at directly (read-only, and not in the body schema).
- Mixed PATCH (status + note): one audit row or two? Recommend one row per distinct action: bug_report.resolved (done), bug_report.reopened, bug_report.note_updated, in the same transaction, metadata ids and status only: {report_id, app_id, from_status, to_status}; note edit metadata is {note_changed: true}, with no text, no length. A no-op writes none, and a note set to the same value is a no-op. Add the three actions to tests/test_audit_coverage.py's coverage list and to the audit action catalogue/docs if one exists (grep audit action enumerations).
- Reopen keeps resolution_note (it is useful history) unless Ming says otherwise; the ticket says reopen "clears both" (handler and handled_at) only. Mark done does not require a note.
- 404 for unknown id; also 404 for a malformed UUID? FastAPI gives 422 for a non-UUID path param, same as other modules; keep that.
- OpenAPI contract test: add the new routes, responses (200, 401, 403, 404, 412, 422), and the If-Match parameter, as in the entitlements precedent.

HTML / metacharacter handling (security-review item)
- The API should return the values verbatim as JSON strings (JSON encoding handles quotes and control characters). Do NOT HTML-escape on the server: escaping in the API would double-escape in any client that already escapes and corrupts data for non-HTML consumers. Escaping is the renderer's job; this is the standard rule.
- Make this explicit and enforceable: (a) document in the OpenAPI field descriptions of description, page_url, app_version, user_agent, resolution_note that they are untrusted plain text, never HTML, to be rendered as text; (b) Content-Type application/json plus X-Content-Type-Options: nosniff (check that the app already sets it globally); (c) page_url is returned as a string only, no pre-built link field; its http/https scheme is already enforced at write time, which is what admin-pan relies on before making it a link (rel="noopener noreferrer"); (d) add a test where a report containing <script>, quotes and & in app_version/page_url path/description round-trips unchanged through list and detail (proves no mangling and documents the contract); (e) record a follow-up for admin-pan (outside this repo) to render everything as text.
- Optional hardening (consider, not required): tighten the app_version rule to a version-like charset (e.g. ^[A-Za-z0-9._+\- ]{1,64}$) so that HTML metacharacters cannot enter at all. That is a validation tightening on a table that has few or no rows now, and ADM-028 is merged; changing it is a v1 contract tightening on a recently shipped write endpoint, and would also need a DB CHECK/migration. It is the one thing I would raise to Ming rather than decide; keep out of the diff otherwise (R7).

RISKS

- Mixed bearer and cookie routers; keep apart or tests/test_route_auth_classes.py fails.
- ETag only meaningful if updated_at really changes on every write and never on a no-op; test both.
