# Consult — api-platform-engineer — USR-23 (2026-11-19)

## Findings

- No admin Bearer membership or invitation routes exist. Invitations live in `app/modules/invitations/` (model, repository and service; schemas hold only the cookie-route DTOs). The model `OrgInvitation` has `org_id`, `app_id`, `role_id`, `email_hmac`, `token_hash`, `invited_by`, `expires_at`, `accepted_at`, `accepted_by`, `revoked_at` and `created_at`. Role and app are reachable via the composite FK `(role_id, app_id)` to `roles`.
- Indexes: `ix_org_invitations_org_id_created_at` already serves the list query (filter by org, order by created_at). `role_assignments` has `ix_role_assignments_org_id`. There is no composite index on (org_id, created_at); I see no need for one, so **no migration** is expected (the R2/High-path trigger is avoided unless the planner adds an index).
- `RoleAssignment` has `user_id`, `role_id`, `org_id` (nullable; org-scoped means not null), `granted_by`, `expires_at` and `created_at`. It has no `app_id` column, so the app comes from `roles.app_id` joined to `apps.key`. The unique key on (user, role, org) means a user with two roles gives two rows.
- `User` has `email` (CITEXT), `status` (active or disabled) and `display_name`.
- The pattern to copy is `app/modules/rbac/assignments_router.py`: `router = APIRouter(prefix=..., dependencies=[Depends(current_admin)])`, `**require_permission("admin:users:read", errors={404: ...})`, `Page(items, total, limit, offset)` and `PageDep`. For an org 404, `app/modules/organizations/router.py` uses `_route(READ, _NOT_FOUND)`, `OrganizationService.get`, and `READ`/`WRITE` constants.
- `Cache-Control: no-store` is set by injecting `response: Response` and setting `response.headers[...]` (see `app/modules/admin_auth/me_router.py:24`).
- The invitation repository already has the exact "pending" predicate: `accepted_at IS NULL AND revoked_at IS NULL AND expires_at > func.now()`. `db_now()` and the supersede update are there too. Audit actions `ORGANIZATION_INVITATION_REVOKED` and `AuditTarget.INVITATION` already exist, and a revoke audit record is written in `_supersede` with `changes={"reason": ...}`, `org_id` and `app_key`. That makes the optional DELETE cheap.

## Recommendations

1. **Where it lives.** Add the two GET routes to the organizations module, e.g. a new `app/modules/organizations/members_router.py` (prefix `/organizations`, `current_admin` dependency) registered in the v1 aggregation. Do not use `/organizations/{id}/…` handlers in `invitations/router`. Layering (R1): router → `OrganizationService` (404 via the existing `get`) → repository methods that do SQLAlchemy only. Put the members query in `organizations/repository.py` and the invitations query in `invitations/repository.py`. Check the circular-import risk between the organizations and invitations modules.
2. **Members query.** A single SELECT joining `role_assignments`, `users`, `roles` and `apps`, with `WHERE org_id = :id`. Filters: `app` (validated with `APP_KEY_RE`, applied as `apps.key = :app`) and `active` (`expires_at IS NULL OR expires_at > now()` for true, the inverse for false; use the database clock `func.now()`, not Python time). Count with the same WHERE. Use a stable order (`created_at, id`) so paging is deterministic. No N+1.
3. **Invitations query.** Select from `org_invitations` joined to `roles` and `apps`. Do not load or select `email_hmac`/`token_hash` into the response model; use explicit columns or a column-limited select. Derive `status` in SQL with a CASE, in priority order: accepted_at → `accepted`; revoked_at → `revoked`; expires_at <= now() → `expired`; else `pending`. The accepted/revoked check comes first so an accepted invitation that later passes its expiry stays `accepted` (the DB CHECK guarantees accepted and revoked never both hold). Apply the `status` filter by reusing the same expression, with Python-side enum validation (`Literal` or `StrEnum`) so an invalid value is 422. Sort `created_at desc, id`. Also expose `app` (key) in the response. The ticket lists `role_key` only; `app_id` is an internal detail.
4. **Schemas.** Pydantic with `extra="forbid"` is not needed for responses, but use explicit read models (`OrgMemberRead`, `OrgInvitationRead`) with no `email`, `token*` or `email_hmac` fields. A test should assert the exact key set of the JSON, not only the absence of known fields.
5. **Permissions (R3).** Members use `admin:users:read` (as ticketed). Invitations use `admin:organizations:read`. Confirm both permissions exist in the admin seed. Both are already used elsewhere, so no catalog change is expected. Members expose user PII (email, display name), which is why `admin:users:read` is the right gate; the planner should note that an `admin:organizations:read` holder alone cannot see members.
6. **Optional DELETE.** Cheap, so recommend including it. Route `DELETE /organizations/{org_id}/invitations/{id}`, `admin:organizations:write`, 204. The service takes a row lock with `with_for_update` and filters by `org_id` and `id` (404 for unknown org or invitation, or one belonging to another org). Behavior when the invitation is not pending needs deciding (see Open questions). Revoke with a conditional UPDATE (`accepted_at IS NULL AND revoked_at IS NULL`, `revoked_at = now()`), then in the same transaction `audit.record(ORGANIZATION_INVITATION_REVOKED, actor=principal, ctx=ctx, target=(INVITATION, id), app_key=..., org_id=..., changes={"reason": "staff_revoked"})`. The audit `actor` type for an admin principal is the one used in `AssignmentService` (`actor=principal`), not `EndUser`. Mirror the `AssignmentService` call style. If included, tests: 204, audit row, a second DELETE, an accepted invitation, a foreign org, 401/403.
7. **Tests (R8).** Cover: 401 and 403 for each route (including a token with only `admin:organizations:read` getting 403 on members); 404 unknown org (and invalid UUID → 422); paging (`limit`, `offset`, `total`, limit > 100 → 422); a user with two roles giving two rows; an expired assignment shows `active=false` and the `active` and `app` filters work; each invitation status (pending, accepted, revoked, expired) and the `status` filter; no token fields and no email in the body; `Cache-Control: no-store` on members; a query-count check for N+1 if a helper exists in the test suite. Rows from another org must not leak.
8. **Docs/contract.** Update the OpenAPI summaries/descriptions, declare 404 in `errors`, and add the new endpoints to docs (`docs/identity-architecture.md` API section or wherever endpoints are listed) and `work/backlog.md` notes. Note R9: the paths are `/api/v1/organizations/{org_id}/members` and `.../invitations` (plural nouns, OK, no exception needed).

## Risks

- Invitation `status` derived from the DB clock can flip between `pending` and `expired` across requests; document it as computed at read time. The `expired` status is not stored.
- Without a stable tie-breaker, paging may duplicate or skip rows; use `id` as the final sort key.
- PII: the members list exposes emails to anyone with `admin:users:read`; audit read access is not required by R4 (reads). Setting `no-store` on members only was specified, but invitations carry no PII, so `no-store` there is optional. Cheap to add for consistency, so recommended.
- `granted_by` and `invited_by` are SET NULL on user deletion, so they can be null; the response models must allow it (`uuid | None`). The same applies to `accepted_by`.
- An org-scoped assignment can reference an expired role; no issue, but joins to `roles` use the plain FK so there is no orphaning risk.
- The ticket path is a High-path area (auth, tokens/RBAC): the tags are `auth`/`security`, so planning stops for owner approval, and an `appsec-engineer` security review is expected. No migration is planned, which keeps the footprint small.
- If the DELETE is included, concurrency with accept: use the same conditional-UPDATE (as `consume`) so a concurrent accept and revoke cannot both succeed.

## Open questions

1. Include the DELETE in this ticket (recommended, small) or move it to a follow-up?
2. DELETE on a non-pending invitation (accepted, revoked or expired): 409 (a new conflict code) or idempotent 204 for already-revoked? Recommend 409 for accepted, idempotent 204 for revoked, and allow revoking an expired-but-unaccepted invitation (harmless).
3. Should the members list show disabled users (`user_status` is returned, so yes by default), and should `active` also account for user status? Recommend: no, `active` means "assignment not expired" only, as the ticket says.
4. Should members be restricted to org-scoped assignments only (`org_id = :id`)? The ticket says so; app-scope assignments (null org) are excluded by construction.
5. Default sort for members (suggest `created_at desc, id`) and whether `sort` should be a parameter; the ticket doesn't list one, so recommend none.
