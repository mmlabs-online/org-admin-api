## §1 Problem

mmlabs runs several products/services. Admin tasks (managing customer orgs, users, which products an org can use, support actions) are spread across each product, with no single place, no shared permission model, and no audit trail of who changed what.

## §2 Goals

- One admin API that the mmlabs admin web UI (and internal tools) use for cross-product administration.
- **mmlabs Identity:** one user account for the whole mmlabs ecosystem, with email + password managed by this service, and tokens every mmlabs app can verify (owner, 2026-11-11; §5.8).
- A shared permission model for internal staff.
- A complete, queryable audit log of admin actions.

## §3 Non-goals (v1)

- ~~End-user (customer) login/auth for the products themselves.~~ Removed 2026-11-11 (owner): end-user identity is now in scope, see §5.8.
- Social login (Google, Apple…), acting as a full OIDC/OAuth2 provider, and a hosted login UI — not in v1 of §5.8. Each app keeps its own login page (2026-11-11, D1/D4).
- Migrating users from Supabase Auth (working assumption OQ2: existing users re-register).
- Billing / payments.
  > 2026-11-18 (owner, OQ57): this non-goal **stands**. §5.14 covers non-monetary AI usage limits and usage tracking per user and app only; prices, paid plans, buying tokens, payment providers and invoices are out, listed in §5.7 Later ("not now").
- Replacing each product's own internal data model.

## §4 Actors

| Actor | Wants to… | So that… |
|---|---|---|
| Super admin | manage staff accounts and their roles | access follows least privilege |
| Support staff | look up an org and its users, suspend/reactivate | tickets get resolved quickly |
| Ops / product owner | enable/disable a product for an org, set plan/limits | customers get the right entitlements |
| mmlabs services | read an org's status and entitlements | products enforce what admin decided |
| Auditor | see who did what and when | changes are accountable |
| App admin (2026-11-18, §5.14; holds `<app>:usage:manage` in that app, OQ61, 2026-11-20) | set an app's AI usage defaults and grant tokens to its users | one app's usage is managed without super-admin rights |

## §5 Features

### §5.1 Organizations — *done (ADM-001)*
CRUD for organizations (slug, name, description, status `active`/`suspended`). Paginated list.
> 2026-11-19 (ADM-024, owner): GET/PATCH (and POST 201) return a strong ETag derived from updated_at; PATCH accepts optional If-Match (strong comparison, * = any) and answers 412 precondition_failed with the current ETag when stale, changing nothing; without If-Match behaviour is unchanged. 412 joins the error codes (R6).
> 2026-11-11 (D10, D15): this table moves to the Identity module (USR-06), gains `created_by`, keeps `description` and `status`; apps use it per `apps.org_mode`.
> 2026-11-17 (USR-06a, done): owned by Identity (D15 = ownership; code stays in `app/modules/organizations/`), `created_by` added, FK from `role_assignments.org_id` (RESTRICT; admin delete with assignments answers 409 `org_has_assignments`). End-user create/list and org-scoped tokens: ADR-0013. Invitations: USR-06b.

### §5.2 Staff authentication
Only authenticated mmlabs staff can call `/api/v1/*`. Health endpoints stay public. Approach (SSO/OIDC vs. other) is an open question (§8 Q2).

### §5.3 Authorization — multi-app RBAC (owner, 2026-11-11; [ADR-0001](adr/0001-multi-app-authorization.md))
One model for every mmlabs app, the admin API included (app `admin`). Apps are registered; each app declares namespaced permissions (`<app>:<resource>:<action>`) and its own roles; users get roles per app, optionally limited to one organization. Every admin `/api/v1` endpoint declares the `admin:*` permission it needs, except self-scoped reads of the caller's own authorization (`GET /api/v1/me/permissions`, ADR-0008). A bootstrap super-admin (`admin:*`) exists. Business rules on an app's own data stay in that app.

Membership (2026-11-11, D8–D10; details in [`identity-architecture.md`](identity-architecture.md)): each app has a `join_policy` (`open` | `approval` | `closed`; default `open`, `admin` = `closed`), a default role `<app>:member` holding all its permissions except those flagged `is_admin` (for `org_mode = required` apps also except org-level permissions, `permissions.scope = 'org'`; ADR-0015; owner, 2026-11-17), an `org_mode` (`none` | `required`; calechip = `required`) and its allowed browser `origins`. Joining assigns the default role at app scope (`org_id NULL`). Policy and role contents are data. The role catalog `GET /api/v1/apps/{key}/roles` is public (D17); app origins are limited to `mmlabs.online`, its subdomains and localhost (D19).

> 2026-11-18 (USR-18): staff apps list filters `status`, `join_policy`, `org_mode`, `q` (key or name, trimmed 1..100, empty → 422) and `sort` (allow-list, default `key`, `id` tie-breaker).

> 2026-11-19 (USR-24): roles.updated_at now also moves when a role's permission set changes (staff PUT, manifest, default-role rebuild); GET /api/v1/apps/{key}/role-definitions/{role_id} and PUT …/roles/{role_id}/permissions return a strong ETag derived from it; the PUT accepts optional If-Match with the ADM-024 rules (412 precondition_failed with the current ETag, nothing changed); RoleRead gains updated_at.

### §5.4 Audit log
Append-only record of every mutating admin action: actor, action, target type/id, before/after (or diff), timestamp, request id. Read-only, filterable listing for auditors.
> 2026-11-18 (ADM-022, owner): staff export the filtered audit log as CSV with GET /api/v1/audit-logs/export (admin:audit:read; same filters as the list; newest first, at most 10,000 rows, truncation signalled by X-Export-Truncated; each export writes an audit_log.exported entry). Part of the audit log, separate from the §5.11 reports, which stay undecided.

### §5.5 Products registry — merged into the apps registry of §5.3 (2026-11-11)
The list of mmlabs products is the `apps` table of §5.3 (key, name, status).

### §5.6 Org product entitlements
Which org can use which product, with plan and limits; enable/disable per org. Readable by mmlabs services through the `ent` access-token claim (§8 Q4, ADR-0017).

> 2026-11-19 (ADM-024, owner): GET/PATCH (and POST 201) return a strong ETag derived from updated_at; PATCH accepts optional If-Match (strong comparison, * = any) and answers 412 precondition_failed with the current ETag when stale, changing nothing; without If-Match behaviour is unchanged. 412 joins the error codes (R6). New GET /api/v1/organizations/{org_id}/entitlements/{entitlement_id} (admin:entitlements:read).

> 2026-11-17 (ADM-006): staff Bearer endpoints under /api/v1/organizations/{org_id}/entitlements (admin:entitlements:read|write). Active = enabled AND org active AND app active (?active=true). Only non-admin, active, org_mode=required apps can be granted. ADM-018: services read it through the `ent` claim (Q4, ADR-0017).

> 2026-11-18 (ADM-019): `PATCH /api/v1/apps/{key}` changing `org_mode` from `required` to `none` is refused with 409 `org_mode_in_use` while the app has org entitlements or org-scoped role assignments (owner, 2026-11-17).
> 2026-11-18 (ADM-020): staff list filters `status`, `q` (name or slug, trimmed 1..100, empty → 422) and `sort` (allow-list, default `-created_at`, `id` tie-breaker).
> 2026-11-18: per-user (never per-org; owner, OQ53) AI usage limits are §5.14; they do not change this section or the `ent` claim.

### §5.8 mmlabs Identity — ecosystem users and authentication (owner, 2026-11-11)
One account per person across all mmlabs apps, **fully self-hosted here** (D1): email + password only, no external IdP, no social login, not an OIDC provider. Architecture, data model, API and decision log D1–D12: [`identity-architecture.md`](identity-architecture.md).

- **Users:** email (unique, case-insensitive), password, status (`active` / `disabled`), email verified flag, timestamps. Staff are users too; what they may do in the admin API is RBAC (§5.3).
- **Sign-up:** open self-registration, protected by Cloudflare Turnstile and a per-IP rate limit (D2). Unverified users may log in but must verify their email before joining any app or getting an app token.
- **Passwords:** hashed with Argon2id; never logged or returned; minimum length and a breached/common-password check per the plan.
- **Login and sessions:** each app has its own login page and uses `@mmlabs/auth-client`, which posts credentials straight to this API (D4). A browser holds one device session (cookie `__Host-mm_device`, rotated with a 60 s grace) with any number of signed-in accounts; each app remembers its own chosen account, so signing into another account in one app does not change another app (D5, D6). Logout per account or for the whole device.
- **Per-app access tokens:** an app asks for its own per-app access JWT (lifetime `ACCESS_TOKEN_TTL_SECONDS`, up to 12 h; 12 h in production (owner, 2026-11-17)) for a chosen account (and org, if any), carrying only that app's roles (D7). Not a member → `not_member` with `join_available`; joining follows the app's `join_policy` (D8–D9).
- **Verification by apps:** public keys at `/.well-known/jwks.json`; apps verify signature, `iss`, `aud` and expiry locally. Claims: `sub`, `email`, `email_verified`, `aud`, `roles` (app-scope plus selected-org roles), `org` (if scoped), `org_roles` (if scoped: role keys held in that org only; org apps authorize org data from it, ADR-0015) (owner, 2026-11-17), `ent` (if scoped: `{plan, limits}` of the org's active entitlement for the app, else `null`; ADR-0017), `iat`, `exp`. Backends use `mmlabs-auth` (Python) (D4).
- **Abuse protection:** no hard lockout; per-email exponential backoff after 5 failures (cap 15 min), per-IP limit, Turnstile after 3 failures; the same error for unknown email and wrong password (D11). CORS only for registered app origins; cookie-authenticated POSTs check Origin and `X-MM-App` (D12).
- **Email flows:** email verification and password reset by one-time, expiring links, sent through Gmail SMTP behind an `EmailSender` interface; resend at most 1/min and 5/day per email (D3).
- **Organizations:** optional per app (`org_mode`); one `organizations` table owned by this Identity module (D10, D15, USR-06).
- **Endpoints:** all under `/api/v1/auth/*` (cookie `__Host-mm_device`, `Path=/`, host-only; D13 as amended by D20); JWKS at `/.well-known/jwks.json` (D13).
- **Admin:** staff can list, look up, disable/enable users, manage their roles per app and revoke their sessions (audited, §5.4). Session list and revocation per user: §5.10.

### §5.9 Admin UI read models — dashboard stats and per-app member counts (owner idea, 2026-11-16; draft)
Context (owner, 2026-11-16): the admin UI **`admin-pan`** (repo `mmlabs-online/admin-pan`, served at `https://admin-portal.mmlabs.online`) is a browser SPA that calls this API with Bearer `aud=admin` tokens. Its mock screens need the read models below. Field names are **snake_case** (owner, 2026-11-16), like the rest of v1.

**Prerequisite — browser access for admin routes.** Today CORS covers `/api/v1/auth/*` only (ADR-0006); admin routes send no CORS headers, so a SPA on another origin cannot call them. Owner note (2026-11-12, ADM-002 ticket, USR-03e A1): "if an admin web UI needs cross-origin Bearer calls, add non-credentialed CORS from `apps[admin].origins`". So: `https://admin-portal.mmlabs.online` is registered as an `admin` app origin (CLI `set-admin-origins`), and admin routes answer CORS for those origins only, **without** credentials (Bearer in the `Authorization` header, never the cookie). The SPA gets its `aud=admin` token through the existing `/api/v1/auth/*` flow with `X-MM-App: admin`.

**Dashboard stats** — one read-only document for the dashboard screen (a single document, not `Page[T]`: an R9 exception to record like D18). Every number comes from data that already exists; counts are returned as breakdowns so the UI, not this spec, chooses what a tile shows:

| Tile (admin-pan) | Source | Computable today? |
|---|---|---|
| Total users | `users` — total, by `status` (`active`/`disabled`) | yes |
| Unverified users | `users.email_verified_at IS NULL` | yes |
| Active / suspended orgs | `organizations.status` (`active`/`suspended`, §5.1) | yes |
| Apps | `apps` — total, by `status` | yes |
| Sign-ins, last 24 h (succeeded / failed) | `audit_log` rows `auth.login_succeeded` / `auth.login_failed` in a rolling 24 h window (event counts, not distinct users) | yes, with caveats below |
| Sign-ups per month | `users.created_at` grouped by calendar month | yes (last 12 months, month boundaries in `Asia/Ho_Chi_Minh`: OQ6, decided 2026-11-17) |
| Members per app | same definition as the per-app member count below | yes (OQ5 definition, decided 2026-11-17) |

Caveats to keep visible in the UI and API docs: failed sign-ins include unknown emails (anonymous actor) but **not** requests refused with 429 or by Turnstile (ADM-004b writes nothing for those); sign-up counts include self sign-ups and CLI-created accounts, and do not depend on the audit log (whose retention is ≥ 90 days, ADM-004c). Reads must meet §6 (p95 < 200 ms) — the planner checks that the audit-log count is index-backed.

**Per-app member count** — the "Members" column of the Apps screen: an additive `member_count` field on the existing staff apps list and app detail (no new endpoint, no breaking change in v1). Definition (owner, 2026-11-17, OQ5): a member is a distinct user with at least one non-expired role assignment on the app (app scope or any org); only users with status `active` count (unverified email still counts); the `admin` app shows its count (= staff).

Permission (owner, 2026-11-17, OQ4): new permission `admin:stats:read` for the dashboard stats document (counts only, no audit rows exposed); `member_count` uses the existing `admin:apps:read`. Read-only, so no audit entry (R4 covers mutations only).

> 2026-11-17 (ADM-015): `GET /api/v1/stats/dashboard` (admin:stats:read, is_admin, granted to no role; a single document, R9 exception D26). Sign-ups: last 12 months including the current partial month, boundaries in Asia/Ho_Chi_Minh. Sign-ins: 24 h totals (succeeded / failed), not split per app.

### §5.10 Staff session management (owner idea, 2026-11-16; draft)
Staff can see a user's signed-in sessions and sign them out — completes the "revoke their sessions" line of §5.8 Admin.

- **List** a user's account sessions (paginated), each with: account session id, created / last used, its device session's last seen, IP and user agent (from `device_sessions`), and revoked state. Default: non-revoked only.
- **Revoke one** account session, and **revoke all** of the user's account sessions on every device (the same effect as a password reset, USR-04b). Staff revoke **account** sessions, not device sessions: a device session may also hold other people's accounts on a shared browser, and they must stay signed in.
- **Permission `admin:*`** (owner, 2026-11-16) for list and revoke.
- **Audited** (R4, §5.4): one entry per revoke action in the same transaction, actor = staff user, target = the user; `changes` carries session ids / counts only, never IPs, user agents, cookies or tokens. New action names are set at PLAN (e.g. `user.session_revoked`, `user.sessions_revoked`).
- **Known limit (no refresh tokens, D7):** access tokens already issued stay valid until they expire (up to `ACCESS_TOKEN_TTL_SECONDS`: 12 h in production (owner, 2026-11-17); admin role revoke and disable still apply on the next admin request, ADR-0008 §3). Revocation stops new tokens; it does not kill live app tokens. Admin (`aud=admin`) tokens carry `sid` and end on the next admin request after logout, password reset, staff session revoke or disable (USR-14). Whether the remaining limits are acceptable for admin tokens: §8 OQ8.
- **USR-10 (owner, 2026-11-17):** `GET /api/v1/users/{id}/sessions` (active sessions only; fields `id`, `created_at`, `last_used_at`, `device_last_seen_at`, `ip`, `user_agent`; `Cache-Control: no-store`), `DELETE /api/v1/users/{id}/sessions/{session_id}` and `DELETE /api/v1/users/{id}/sessions` (revoke one / all; 204). All three need `admin:*`; staff cannot use them on themselves (403 `self_session_change_forbidden`). Audit actions `user.session_revoked`, `user.sessions_revoked` (ids capped at 100, exact count); a revoke that changes nothing writes no row. Revoking sessions stops the user from getting **new** access tokens (`/auth/token` -> 401 `session_invalid`) and ends the user's admin (`aud=admin`) tokens bound to those sessions on their next admin request (USR-14). Tokens of other apps stay valid until `exp`, at most `ACCESS_TOKEN_TTL_SECONDS` (12 h in production) plus 30 s leeway. It does not stop a new sign-in with the password. IP and user agent are recorded when the browser first signed in and are shared by every account on that browser.
- Open: Q6 (showing IP / user agent to staff is PII).

### §5.12 Bug reports from apps (owner idea, 2026-11-19; **scope decided 2026-11-19**)
Owner's idea (2026-11-19, translated from Vietnamese): *"I want to add an API so users can report bugs for mmlabs apps. E.g. from the ricotdin app, a report calls the API with app name = ricotdin. This API is accessed by everyone who has an admin role. In admin-pan, staff see all reports from every app. For a report, the user can describe the bug, paste a screenshot, or upload videos/images. Record the account that reported it. When it is handled, mark it done and record the account that marked it done (the handler)."*

**Decided scope for v1 (owner, 2026-11-19).** All of §8 OQ19–OQ35 are answered. In the owner's words (translated): *"mmlabs staff handle reports; agree with all [the recommended answers]; lower [the image limit] to 5 MB."* Implementation details not fixed below (exact rate-limit numbers, description length, field caps, table shape) are PLAN's.

**Not in v1** (§5.7 Later): video attachments, a reporter "my reports" view, staff delete of reports or attachments, notifications (reporter or staff), a dashboard tile.

Not to be confused with the internal `BUG-XXX` workflow tickets of this repo (ADR-0012): those are developer tickets in `work/`; §5.12 is end-user feedback stored by the API.

**Problem (owner, 2026-11-19, OQ19).** End users of mmlabs apps have no in-app way to report a problem, and staff have no single place to see and close reports across apps. **mmlabs staff** triage the reports in admin-pan. **"Done" means handled**: the problem was fixed or the report was answered. No volume target is recorded. **Placement (OQ33):** the feature lives in this API.

**Two sides:**
- **Submit — end users inside an app** (e.g. ricotdin) (owner, 2026-11-19, OQ20/OQ21). The app's browser posts **directly** to `/api/v1/auth/bug-reports` in the **cookie class** (R3 class 2, the same pattern as join and org create): `mm_device` cookie, `Origin` check, `X-MM-App: <app>`. No new auth class. The reporter must be **signed in** (account session), **active**, have a **verified email**, and be a **member of that app**. "This API is accessed by everyone who has an admin role" applies to the staff side only. Staff do not file reports from admin-pan (OQ21).
- **Triage — staff in admin-pan** with Bearer `aud=admin` tokens (R3 class 1): list all reports from every app, open one, view its attachments, mark it done or reopen it, and keep a resolution note (owner, 2026-11-19, OQ22, OQ25). Two new admin permissions: **`admin:bug-reports:read`** (list, detail, download attachments) and **`admin:bug-reports:write`** (mark done / reopen). The owner chooses which staff roles get them; `admin:*` covers both. Both keys follow the ADR-0003 grammar (hyphen, not underscore).

**A report:**
- `id` (UUID), `app_key` (a registered app), reporter account (`user_id`), description (text; length limit set at PLAN), attachments (0..5 images, including a pasted screenshot; see attachment limits below), `status`, `created_at`.
- On "done": the handler account (`handled_by`) and `handled_at`; an optional staff **resolution note** (OQ25).
- **Optional context (owner, 2026-11-19, OQ26)**, sent by the app, all optional: `org_id` (for org apps), **page URL** (stored as scheme, host and path only; query string and fragment are dropped), **app version**, **user agent** (capped length). No user-chosen severity or category in v1.
- **App binding (owner, 2026-11-19, OQ20, OQ21):** the app comes from `X-MM-App` **after the `Origin` check**, never from the body, so a user cannot file reports under another app. The reporter must be a member of that app. Consequence: unverified or non-member accounts cannot report (including sign-in or join problems). Disabled or unknown apps are refused, and **the `admin` app cannot be a report target** (`X-MM-App: admin` is refused like other app-scoped cookie endpoints).

**Lifecycle (owner, 2026-11-19, OQ25).** Two states: `open` and `done`. Marking done records the handler (`handled_by`) and `handled_at`. Staff can **reopen** a report (`done` → `open`), which clears the handler and `handled_at`. Staff can write a **resolution note**, visible to staff only. Not in v1: `in_progress`, `wont_fix`, `duplicate`, assignment to a handler, comments, replies to the reporter.

**Reporter side (owner, 2026-11-19, OQ27).** The reporter submits and gets the created report id back (and the per-attachment outcome, OQ35). Reporters **cannot list or view their own reports** in v1, and are **not emailed** when a report is done (§5.7 Later).

**Staff side (owner, 2026-11-19, OQ22, OQ28):** list as `Page[T]` (newest first; filters app, status, reporter, date range), detail, attachment download — `admin:bug-reports:read`; mark done, reopen, edit the resolution note — `admin:bug-reports:write`. The reports themselves are user content in their own table, **not** audit rows. **No staff delete** in v1 (§5.7 Later).

**Link to the release the user ran (owner, 2026-11-19; cross-reference §5.13).** The staff report read (detail, and the list items) links each report to an `app_releases` record of its app, so staff see which release the reporter was running:
- **First, the report's app version** (the optional OQ26 context field): if it equals the `version` of a release record of that app, that record is linked and **`release_match = reported`**.
- **Else, the release live at report time:** the record of that app with the latest `deployed_at` ≤ the report's `created_at` among `status = deployed` (the §5.13 "live now" rule, evaluated at `created_at`) → **`release_match = inferred`**.
- **Else** (no matching version and no deployed release before the report) → **`release_match = none`**, no linked release.
- The response exposes `release_match` (`reported` | `inferred` | `none`) and the linked release's id and version (or null). The link is informational; it never blocks submit or triage, and a missing release table row is not an error.
- **Environment (open, not blocking — §8 OQ50):** a report carries no environment. Proposed default: a reported version matches by grammar (`vX.Y.Z` → `production`, `sha-…` → `staging`); the `inferred` rule uses `production` only.
- **Facts carried into PLAN:** (1) §5.13 keeps only the latest deploy of each release (a redeploy or rollback moves `deployed_at` forward), so an `inferred` link computed after a later redeploy/rollback can name a different release than the one live at report time; storing the link when the report is created avoids that but ties the bug-report submit (ADM-028) to the release table — **compute-at-read vs store-at-create is PLAN's choice**. (2) A staff-deleted release (§5.13 OQ42) drops a `reported`/`inferred` link (falls back to the next rule, or `none`). (3) The app version is free text; whether a missing leading `v` is normalized before matching is PLAN's.
- **Owner:** ADM-029 (staff read) if the release table (ADM-033) is merged by the time ADM-029 is planned; otherwise a **small follow-up ticket** after both ADM-029 and ADM-033. **Default: the follow-up ticket** — by the board's pick order (both P2, ADM-029 sits above ADM-033), ADM-029 runs first.

**Audit (owner, 2026-11-19, OQ28).** Report creation writes an audit entry `bug_report.created` in the same transaction, carrying ids and counts only (report id, app key, reporter id, attachment count), never the description, context fields or attachment content. Every staff state change (done, reopen, note edit) writes an audit entry in the same transaction (R4, §5.4), again ids and status only. Staff reads and attachment downloads are **not** audited.

**Retention (owner, 2026-11-19, OQ29).**
- **Attachments** are deleted (permanent Drive delete) **90 days after the report is marked done** (counted from `handled_at`; a reopen clears `handled_at`, so a reopened report keeps its attachments until it is done again).
- **Reports** are deleted **365 days after creation**, whatever their state, together with any remaining attachments.
- Attachment metadata rows stay after their Drive file is deleted, with a **deleted marker**, until the report itself is deleted.
- Reports of a **disabled reporter stay** and follow the same retention.
- Retention runs as a scheduled purge (CLI / job); it is part of v1 scope, together with the Drive file deletes it triggers.

**Abuse (owner, 2026-11-19, OQ30).** Per-IP and per-user rate limits on submit, in-process like the identity controls (ADR-0002). At most **10 reports per user per 24 h**, and a **cap on open reports per user per app** (number set at PLAN). **No Turnstile** on submit in v1.

**Notifications and dashboard (owner, 2026-11-19, OQ31, OQ32).** No staff notifications in v1 (admin-pan only). No dashboard tile or Apps-screen count in v1.

**Attachments unavailable (owner, 2026-11-19, OQ35).** If the Drive keys are not set (attachments off) or Drive fails at submit time, the report is **still accepted as text**; the response tells the app which attachments failed. In admin-pan, a report whose Drive file is missing shows **"attachment unavailable"** for that file instead of failing the page.

Design facts and decisions carried into PLAN:
- **Submit auth class — cookie class (owner, 2026-11-19, OQ20).** Chosen over a per-app Bearer token (new auth class), the app credential (would widen ADR-0016 and let the app backend assert the reporter) and anonymous submission (contradicts recording the reporter). Facts that follow: the route sits under `/api/v1/auth/*` although it is not an identity action; it works for browser apps using `@mmlabs/auth-client`; attachment uploads sent with the cookie need the same CORS (`apps.origins`) and CSRF (`Origin` + `X-MM-App`) checks as every other cookie POST (R11). Since R3 class 2 lists its endpoints, adding `bug-reports` to that list (and recording the choice in an ADR or the decision log) is part of the first ticket.
- **Attachment storage — Google Drive (owner, 2026-11-19, OQ23):** *"Files are stored in Google Drive, like the tudocuatui app does."* Read as: reuse the TuDoCuaTui pattern (`mmlabs-online/tudocuatui`, its D27/D28/D34, `server/drive.js`). The pattern, as facts to carry over (details are PLAN's, not decided here):
  - **Client:** Drive v3 REST over plain HTTP, no Google SDK. `httpx` is already a runtime dependency of this API, so no new library is needed (stack rule holds). OAuth scope `drive.file` (the app sees only files it created).
  - **Config (R5):** four env keys — OAuth client id, client secret, long-lived refresh token, root folder id (all specific to this API, OQ34) — all-or-nothing: none set = attachments off; a partial set = startup error naming the variables only, never values. New keys in `app/core/config.py` and `.env.example`; production values are repository secrets of `mmlabs-online/deployment` written to the env file at deploy.
  - **Files always pass through this API.** Upload: raw-body `PUT` per file, streamed with a byte cap and a magic-byte type check (no browser-to-Drive upload, no presigned URLs, and no multipart parser needed on our side, so `python-multipart` stays out). Download: proxied by this API with fixed safe headers (`nosniff`, CSP `sandbox`, `Cross-Origin-Resource-Policy`); Drive file ids never reach the browser; admin-pan fetches with its Bearer and shows `blob:` URLs (TuDo D34 — `<img>`/`<video>` cannot send a Bearer). No signed URLs.
  - **Layout and consistency (owner, 2026-11-19, OQ34):** files go under this API's **own root folder** (not TuDoCuaTui's), with **one subfolder per app key** (e.g. `<root>/ricotdin/…`, `<root>/tudocuatui/…`); any further split per report (e.g. `<root>/<app_key>/<report_id>/`) is PLAN's choice. Files tagged with Drive `appProperties`. The DB row is written after Drive accepts the file; if the DB write fails the Drive file is deleted; Drive creates are never retried. A sweep CLI (dry-run by default) deletes untracked Drive files older than a grace period.
  - **Size (owner, 2026-11-19, OQ24):** images are capped at **5 MB**, the same as TuDo's multipart cap and Google's documented multipart limit, so **Drive multipart upload suffices** for v1. The Drive **resumable upload** protocol comes with the later video ticket.
- **Implications of Drive (facts, not decisions):**
  - **Google account (owner, 2026-11-19, OQ34):** the **same Google account as TuDoCuaTui**, but a **separate OAuth client** (its own client id / secret and its own refresh token for this API) and a **separate root folder**. This API holds a Google refresh token: a new third-party dependency and a new secret. Credentials and folders are separate from TuDo, so revoking or rotating one app's token does not affect the other; the account itself is shared.
  - **Availability:** a Drive outage or revoked token makes attachments unavailable; reports are still accepted as text and triaged (OQ35, above).
  - **Capacity:** because the Google account is the same (OQ34), the Drive **storage quota is shared with TuDoCuaTui** (and with Gmail/Photos of that account, e.g. 15 GB on a free account); it is the storage cap for all apps' bug-report attachments and TuDo's files together. Drive API quotas / rate limits apply per project and user. **Storage plan unchanged** (whatever plan that account has today; owner, 2026-11-19, OQ34).
  - **Custody (owner, 2026-11-19, OQ34):** the owner holds the Google account and rotates this API's refresh token; rotation is a documented runbook step for the owner.
  - **Backups:** attachments are not in the nightly Postgres backups, but Drive is durable storage, so the backup concern of a local volume does not apply. Restoring the DB from backup can leave rows pointing at deleted files (or files with no row — handled by the sweep).
  - **Deletes are permanent:** retention deletes remove the Drive file for good (OQ29); the same will hold for staff deletes when they come (§5.7 Later).
- **Attachment limits (owner, 2026-11-19, OQ24): images first, video later.** v1 accepts **images only — PNG, JPEG, WebP, GIF — at most 5 MB per file and at most 5 files per report** (so at most 25 MB of images per report; the owner lowered the cap from 10 MB so Drive multipart upload suffices). **Video** (MP4/WebM/MOV, up to 50 MB per file, Drive resumable upload) is a **later ticket** (§5.7). Uploads pass through Cloudflare Tunnel, which caps request body size per plan (100 MB on Free/Pro); both limits fit under it. **EXIF:** apps strip image metadata client-side before upload; this is documented for app teams, and the API does **not** re-encode images. Unvalidated uploads are an attack surface: content-type must be checked by content (magic bytes), not by header; SVG/HTML must not be served inline (stored XSS against staff in admin-pan); downloads served with `Content-Disposition: attachment` / `nosniff`; image metadata (EXIF GPS) may leak location; malware scanning is not available today. Videos shown through a Bearer fetch-to-`blob:` are downloaded whole before playback (no streaming/seek unless the proxy supports range requests).
- **PII** (§8 Q6): descriptions and screenshots may contain emails, other people's data or secrets; with Drive, attachment content lives in a Google account outside the mmlabs Postgres, under Google's terms. Retention bounds this (OQ29, above); since apps strip EXIF and the API does not re-encode, an app that skips stripping can still leak image metadata.
- **Notifications:** none in v1; emailing the reporter or staff would compete with the Gmail SMTP daily limits (D3).

No §3 non-goal conflicts with §5.12: it is not billing, social login, an OIDC provider or a hosted login UI (each app keeps its own report form; this API only receives and stores). It widens the API surface for end users beyond identity (§5.8); the owner confirmed it belongs in this API (OQ33, 2026-11-19).

### §5.13 Release log (owner, 2026-11-19; **scope decided 2026-11-19**)
Owner's request (2026-11-19): *"Release log for every mmlabs app, written by CI and managed only by admin:\* (system super admin)."* Decision record: [ADR-0018](adr/0018-release-log-and-deployer-credential.md) (Accepted 2026-11-19). Owner's answer to OQ36–OQ49 (2026-11-19, translated): *"Agree with everything; the 4 points follow the software architect's recommendation."* — all proposed defaults accepted except OQ37, OQ40, OQ44 and OQ48, which take the software architect's recommendation (below).

**Problem (owner, 2026-11-19).** The owner has no single place that says what each mmlabs app released, when, with which changes, and whether the deploy succeeded. Every production release and every staging build is recorded here and read in admin-pan.

**Decided by the owner (2026-11-19):**
- **Scope:** every app's production releases **and** staging builds. Staging: environment `staging`, version `sha-<7 hex>`. Production: version `vX.Y.Z`.
- **Two writers, both machines, no staff login:**
  - (a) the app's release workflow (GitHub Actions in the app repo), right after it opens the deployment PR, using **that app's app credential** (D25, ADR-0016), accepted **only for its own app**;
  - (b) the deploy workflow in `mmlabs-online/deployment` (self-hosted runner), after the health check, using a **new deployer credential** that may report for any app but **only on the deployment-report route**.
- **Readers/managers:** `admin:*` only (Bearer, `aud=admin`). **No new leaf permission** (no `admin:releases:*`; reconfirmed by the owner, 2026-11-19). No public route, no end-user "what's new".
- **Staging deploys** also go through `mmlabs-online/deployment`, so the deployer reports staging as well as production (owner confirmation, 2026-11-19).
- **Writes never block a release or a deploy:** CI treats any error as a warning and goes on, so both write endpoints are **idempotent and safe to retry**.
- **Machine-credential rules for both writes:** R3 class 4 style (opaque key, SHA-256 hash only), **no CORS**, **per-IP rate limit**, **audited in the same transaction** (R4).
- **Data model** `app_releases`: app (FK, addressed by key), `environment` (`production` | `staging`), `version`, `status` (`pending` | `deployed` | `failed`), `git_sha`, `images` `[{name, digest "sha256:…"}]`, `deployment_pr` (URL on `github.com/mmlabs-online/deployment/pull/N`), `changes` `[{pr_url, title, ticket_id, risk}]` (bounded: ≤ 200 items, title ≤ 200 chars, control characters stripped), `has_migrations`, `created_at`, `updated_at`, `deployed_at`, `deploy_run_url`. **Unique (app, environment, version).** **No commit author emails or other PII.**
- **Create/update** (writer a): idempotent; updating is allowed **only while `status = pending`**, otherwise **409** — except the late-enrichment rule of OQ37 below. Route `PUT /api/v1/apps/{key}/releases/{environment}/{version}`.
- **Deploy report** (writer b): `deployed | failed`, `deployed_at`, `deploy_run_url`. Transitions `pending → deployed | failed`, `failed → deployed` (redeploy); `deployed → deployed` with the **same** `deploy_run_url` is a **no-op 200**, with a **different** one it is a real redeploy or rollback (OQ40 below). If the release record does not exist yet (writer a failed), it is **created from the report** with what is known. Route `…/releases/{environment}/{version}/deployment`; the owner suggested `PATCH`, and `PUT` (upsert) is also acceptable — **PUT vs PATCH is PLAN's choice** (software architect, accepted 2026-11-19).
- **Credentials:** the app credential is widened from "only `PUT …/manifest`" to "**manifest or its own app's releases, by key scope**" (OQ44 below) — this changes R3 in `CLAUDE.md` and is amended through ADR-0018 (ADR-0017 §2 had kept class 4 manifest-only; the owner now widens it for releases only). The **deployer credential** is a new opaque key type (own prefix, SHA-256 hash), **issued, listed and revoked by `admin:*` only** (Bearer endpoints, audited).
- **Staff reads:** list across all apps and per app (`Page[T]`; filters app, environment, status, date range; newest first) and release detail, plus the live-version read (OQ40). Staff delete of a wrong record (audited, OQ42). Documented in OpenAPI so admin-pan generates types (as ADM-013).
- **Bug reports link to releases (owner, 2026-11-19):** the §5.12 staff read links each bug report to the release its reporter ran — the report's app version first, else the release live at report time — with `release_match` = `reported` | `inferred` | `none`. Rules and owning ticket: §5.12 "Link to the release the user ran". The release log adds no route for it.
- **Tests (R8):** happy path; 401/403 for wrong credential type, for another app and for a wrong-scope key; 404 unknown app; 409 status rule (including enrichment conflicts, OQ37); 422 validation of version, digest, URLs and limits; idempotent retry; migration with a working downgrade (R2).
- **Out of scope:** public release notes, webhooks/notifications, editing `changes` after deploy, the admin-pan UI (a separate admin-pan ticket after the API ships).

**Decided details (owner, 2026-11-19 — §8 OQ36–OQ49):**
- **Version grammar (OQ36).** `production`: strict `vMAJOR.MINOR.PATCH`, no leading zeros, **no pre-release or build suffix**. The version is the **git tag** `vX.Y.Z`, not the branch name: the release branch is `release/vX.Y.Z` today (§6.1) and becomes `release/X.Y.Z` (no `v`) in spaceM project-kit 2.0; the API grammar for production stays `vX.Y.Z` either way, so the 2.0 release template sends the tag, not the branch name. `staging`: `sha-` + exactly 7 lowercase hex. A version that does not match its environment's grammar → 422. `git_sha` = 40 lowercase hex, required on the app write; for `staging` the version must equal `sha-` + the first 7 chars of `git_sha` (else 422).
- **Write rules after pending (OQ37; software architect's recommendation).** The app write is a **full replacement** of the release document while `pending`; an identical retry returns 200 with the stored record. Once `deployed` or `failed`, the app write may only **enrich** the record: fields that are still NULL/empty (a record created from a deploy report, OQ38) are filled in from the PUT (200, audited `release.updated`); if **any** non-null field in the record differs from the PUT → **409 `release_not_pending`**, record unchanged; if all non-null fields are identical and nothing is left to fill → 200 no-op (no audit row). The **PUT never changes `status`**. No staff edit endpoint in v1.
- **Record created from a report (OQ38).** The deployer sets only `status`, `deployed_at`, `deploy_run_url` (plus app, environment and version from the path, validated by the same grammar). Everything else stays empty: `git_sha`, `deployment_pr`, `has_migrations` null; `images`, `changes` empty. `deployed_at` is required with `deployed`, refused with `failed`, timezone-aware, at most 5 min in the future and at most 30 days in the past. Reports are accepted for a **disabled** app (the deploy happened); unknown app → 404. Reports for the `admin` app follow OQ48 (its releases are recorded).
- **Extra transitions (OQ39).** `failed → failed` = 200, updates `deploy_run_url` (a retried deploy failed again). `deployed → failed` = **409 `release_already_deployed`**, record unchanged (a failed later redeploy of the same version does not erase that it was live). No `rolled_back` / `superseded` state in v1.
- **Redeploy, rollback and what is live now (OQ40; software architect's recommendation).** `deployed → deployed` with a **different** `deploy_run_url` is a real redeploy or rollback of that version: 200, updates `deployed_at` and `deploy_run_url`, audited `release.deployment_reported`. With the **same** `deploy_run_url` it is a no-op 200 (a retried report; no audit row). So **"live now" per app + environment = the record with the latest `deployed_at` among `status = deployed`**, which stays correct after a rollback to an older version. v1 adds a read for it; the exact shape (list `sort=deployed_at` + a filter, or a small dedicated endpoint) is PLAN's. The redeploy **overwrites `deployed_at`** (one column, latest deploy); naming it `last_deployed_at` instead is a naming alternative left to PLAN — no second timestamp column is added.
- **Retention (OQ41).** Keep all records (production and staging) in v1; no purge job. Revisit with a staging purge when the table passes ~1 GB or ~100k rows.
- **Staff delete (OQ42).** Yes: `DELETE /api/v1/releases/{id}`, `admin:*`, 204, audited. A later retried CI write may recreate a deleted record; accepted.
- **Deployer credential (OQ43).** Format `mmdk_<key_id>_<secret>` (same shape and hashing as `mmak_`), its own table, **at most 2 active** (rotation overlap), no expiry, `last_used_at`, immediate revoke. Issue (value shown once, `no-store`), list (metadata only), revoke: Bearer `admin:*`, audited. **No CLI bootstrap**: the first key is issued through the admin API like app credentials (`docs/deploy.md`).
- **App credential scopes (OQ44; software architect's recommendation).** App credentials gain a **`scope`**: `manifest` | `releases`; each key has **exactly one** scope. Existing keys become `manifest` (migration default). At most **2 active keys per (app, scope)** (rotation overlap per scope). Issuance takes an optional `scope` (default `manifest`, so current clients keep working); list shows it. A key of the wrong scope on a route → **403 `app_credential_scope`**, audited `denied`. Same `mmak_` prefix; the scope is read from the database, not encoded in the key. A `manifest` key is accepted only on `PUT …/manifest`, a `releases` key only on `PUT …/releases/{environment}/{version}`. ADR-0016 §5 issuance rules otherwise unchanged, except that the `admin_app` refusal applies to the `manifest` scope only (OQ48). The app repo holds its `releases` key as **`MMLABS_RELEASE_CREDENTIAL`**, in a **GitHub Environment secret limited to release branches / `main`**; the `manifest` key stays in the deployment repo.
- **Field formats and limits (OQ45).** `changes`: ≤ 200 items; `pr_url` must be `https://github.com/mmlabs-online/<repo>/pull/<N>`, unique within a release; `title` 1–200 chars after control characters (Unicode `Cc`) are stripped and whitespace trimmed; `ticket_id` optional, grammar `^[A-Z][A-Z0-9]{1,9}-[0-9]{1,6}[a-z]?$` (covers `ADM-012`, `USR-05a`, `BUG-003`); `risk` optional enum `low | medium | high` (the risk tiers of `.github/risk-tiers.yml`). `images`: 1–10 items on the app write, `name` a Docker repository name without tag or digest (≤ 255 chars, unique within a release), `digest` `sha256:<64 lowercase hex>`. `deployment_pr`: optional, exactly `https://github.com/mmlabs-online/deployment/pull/<N>`. `deploy_run_url`: required on a report, exactly `https://github.com/mmlabs-online/deployment/actions/runs/<N>` with an optional `/attempts/<N>`. Unknown fields → 422 (no mass assignment).
- **Rate limits and body size (OQ46).** In-process, per IP, before authentication (ADR-0002 pattern), each route its own bucket: app write 30/min, deploy report 30/min. Request body cap 256 KiB (app write) and 4 KiB (report), **checked inside the routes** (software architect, accepted 2026-11-19). Numbers in `app/core/config.py` (R5), final values PLAN's.
- **Audit (OQ47).** One audit row per write that changes something, **ids and status only** (app key, environment, version, release id, status, change count) — never titles or URLs: `release.created`, `release.updated`, `release.deployment_reported`, `release.deleted`, `deployer_credential.issued`, `deployer_credential.revoked`. No-ops (identical retry, `deployed → deployed` with the same `deploy_run_url`) write no row. A valid key used for another app, or a key of the wrong scope, writes a `denied` row (as ADR-0016 §4). Actors are `SystemActor` values: `app:{key}/{key_id}` and `deployer:{key_id}` (`actor_kind = system`, no audit-schema change). App-credential authentication keeps taking `lock_app` (as today) for both scopes.
- **`admin` app and this API's own releases (OQ48; software architect's recommendation).** Releases of this API and admin-pan **are recorded in v1**: `releases`-scoped keys may be issued for the `admin` app (the `admin_app` refusal stays for the `manifest` scope only). **Open for PLAN (not blocking):** org-admin-api and admin-pan both map to the `admin` app and could collide on `(app, environment, version)`; proposed resolution — give admin-pan its own app row or key — decided at PLAN of the releases ticket.
- **Routes (OQ49).** Writes as suggested by the owner (natural-key paths, R9 exception like D18/D25: `{environment}/{version}` instead of a UUID, singular `deployment` sub-document). Staff: `GET /api/v1/releases` (`Page[T]`, filters `app`, `environment`, `status`, `created_from`/`created_to`, `sort=created_at|deployed_at`, default `created_at` desc), `GET /api/v1/releases/{id}`, `DELETE /api/v1/releases/{id}`, plus the live-version read of OQ40 (shape PLAN's); deployer credentials under `/api/v1/deployer-credentials`. Wrong credential type or an admin JWT on a machine route → 401; another app's `mmak_` key → 403 `app_credential_mismatch`; an `mmak_` key of the wrong scope → 403 `app_credential_scope`; disabled app on the app write → 403 `app_disabled` (ADR-0016 §4). The deploy-report method (PUT or PATCH) is PLAN's.

**PII.** No commit author emails, names or GitHub logins are stored; the API cannot detect PII in free-text titles, so the app release template sends PR titles only. Credentials never appear in logs or error details (R5, R11); 422 details name fields, never echo values.

**Cross-repo follow-ups (owner's list, 2026-11-19):**
- **admin-pan:** "Releases" page (list, filters, detail, delete) — separate admin-pan ticket after the API ships.
- **spaceM project-kit 2.0:** release template step in each app's release workflow (`PUT …/releases/…` after the deployment PR is opened; warning-only on error), reading `MMLABS_RELEASE_CREDENTIAL` from a GitHub Environment limited to release branches / `main`.
- **`mmlabs-online/deployment`:** a step in each `deploy-<app>.yml` (production and staging) after the health check (`…/deployment`, `deployed` or `failed`, method as decided at PLAN; warning-only on error).
- **Owner-issued secrets:** `MMLABS_RELEASE_CREDENTIAL` in each app repo (a `releases`-scoped `mmak_` key, GitHub Environment secret limited to release branches / `main`; replaces the earlier `MMLABS_APP_CREDENTIAL` proposal), and `MMLABS_DEPLOYER_CREDENTIAL` in the deployment repo (`mmdk_` key). `manifest`-scoped keys stay in the deployment repo, unchanged.

No §3 non-goal conflicts with §5.13: it is not billing, social login, an OIDC provider or a hosted login UI; the deployer credential is another opaque key, not OAuth client credentials (ADR-0016 §2 holds). It adds no end-user surface. It widens R3 class 4 (owner's decision, recorded in ADR-0018).

### §5.14 Usage limits and credits per user and app (owner idea and answers, 2026-11-18; **scope decided 2026-11-20**)
Owner idea (2026-11-18, translated from Vietnamese): "I want to add a token/billing management feature. The idea is that billing, or the token limits of users on each app, are managed centrally in the admin API." Owner answers to OQ51–OQ60 (2026-11-18) and OQ61–OQ69 (2026-11-20, translated: *"agree with everything"* — every proposed default, i.e. the software architect's recommendation, accepted) are in §8; this section restates them as decided v1 scope. Drafted 2026-11-18 as "§5.12" with OQ19–OQ37 on a branch that was never merged; renumbered 2026-11-20 because §5.12/§5.13 and OQ19–OQ50 are now used (mapping in §8).

**Problem.** mmlabs apps expose AI functions that cost money per use (AI-agent chat, speech-to-text, image analysis). Each app needs to cap how much one user may use, give every new user a free-trial amount, and let staff give more to individual users — managed in one place instead of hard-coded per app. "Token" here means **AI usage units, counted per app in that app's own way**, never the auth access tokens of §5.8 (owner, OQ51).

**In scope (owner, 2026-11-18):**
- **Part A — central limits** and **Part B — central usage tracking / balance**, both (OQ54).
- **App-defined usage metrics.** Each app has its own metrics, each with its own unit, e.g. Ricotdin: number of AI-agent chat turns and duration of speech-to-text; tudocuatui: number of image analyses (OQ51). One configuration model must fit every app; metric keys, units and names below are examples only, not decisions.
- **Subject: user + app, never org** (OQ53). Limits are not tied to `org_mode` and work for `org_mode = none` apps. §5.6 org entitlements (`ent`) are unchanged and unrelated.
- **Default limit per app = free trial.** Each app has a default limit; a user gets it as soon as they sign up / join the app (OQ53).
- **Per-user grants.** Beyond the default, staff grant additional tokens to individual users (OQ53); shape decided in OQ62 below.
- **Reset period:** `daily`, `weekly` or `monthly`; the app's setting (**default `weekly`**, OQ55) is the starting value for each metric, and one metric may differ (OQ64).
- **Who may set limits and grant tokens:** each app's admin and the mmlabs super-admin (OQ52/OQ58), modelled as in OQ61 below. Every change is a mutating admin action → audited (R4), with a required reason (OQ67).
- **Apps fetch limits and report usage through this API** (service-to-service, OQ56). Owner decision (2026-11-18): the R3 class 4 app credential is widened beyond the manifest route for this. Since then ADR-0018 (Accepted 2026-11-19, §5.13) gave app credentials a single `scope` per key (`manifest` | `releases`, at most 2 active per app + scope, wrong scope → 403 `app_credential_scope`) and added a separate deployer credential. Usage calls therefore **add new scopes on the same scoped-key mechanism** — `usage:read`, `usage:write`, `limits:write` (final names set at PLAN) — which **requires an ADR-0018 amendment** and the matching R3 wording in `CLAUDE.md` (ticket **ADM-041**; security-architect + identity-access-engineer), not a fresh widening design. **No usage route ships before that amendment is accepted.** The new scopes are **runtime** keys held by each app backend (unlike the CI-held `manifest`/`releases` keys) and must never reach browser code. Routes and rate limits are PLAN's.
- **Users see their own limits and usage** (OQ59) inside each app in v1 (OQ65).
- **Enforcement on both sides:** the app **and** this API enforce limits, so a user who tampers with an app (client) cannot exceed them (OQ60), through the atomic consume of OQ66.

**Decided details (owner, 2026-11-20 — §8 OQ61–OQ69, proposed defaults accepted):**
- **App admin (OQ61).** An `<app>:usage:manage` permission, `is_admin` (so not in `<app>:member`), held through an **app-scope** assignment only (org-scoped assignments do not count); each app carries it in its own role catalog / manifest. App admins act in the app's own UI; the app backend calls this API with a `limits:write`-scoped key and `on_behalf_of = <user id>`, and this API checks that the user holds `<app>:usage:manage` on that app before applying the change (audit records both the key and the user). App admins may grant to users and change their app's defaults and periods. Super-admin side: `admin:usage:read` and `admin:usage:write` (Bearer, `aud=admin`), both covered by `admin:*`. No new RBAC scoping.
- **Grant shape (OQ62).** "Grant extra" raises one user's per-period limit for one metric, optionally **until a date** (then the app default applies again). A user's limit may also be set below the default, including 0 (blocks that metric). One-off credit packs are later (§5.7).
- **Periods (OQ63).** Calendar periods in `Asia/Ho_Chi_Minh`: daily at 00:00, weekly on **Monday** 00:00, monthly on the 1st at 00:00. No rolling windows.
- **Per-metric settings (OQ64).** Each metric has its own default limit and its own reset period, initialised from the app's period setting (default `weekly`).
- **User visibility (OQ65).** v1: inside each app only — the app backend reads the user's limits and usage with a `usage:read`-scoped key. A central self-read across apps is later (§5.7). Staff see the current period and the retained history (OQ69).
- **Enforcement (OQ66).** The app backend calls an **atomic consume** (metric, amount, idempotency key; `usage:write`-scoped key) **before** the AI action; over the limit → **409 `usage_limit_exceeded`**, nothing consumed; a retried idempotency key returns the first result. Duration metrics consume an estimate first and settle the actual amount after. A failed AI action is **refunded** by the app (same idempotency key). This API unreachable → **fail-closed** by default; an app may opt in (per-app setting) to a **fail-open grace** whose usage is reported later and reconciled (may push the user over the limit for that period). Disabled users and non-members of the app are refused at consume (**403**). Token issuance stays ungated (ADR-0017 §5). The extra call per AI action is accepted; its latency target is set at PLAN.
- **Reason and notification (OQ67).** A reason (1–500 chars) is required on every staff and app-admin adjustment and stored in the audit entry (R4). No user notification in v1.
- **Who defines metrics (OQ68).** Staff define metrics, defaults and periods in the admin API in v1 (`admin:usage:write`); app admins may change defaults and periods of their own app (OQ61). Manifest-declared metrics are later (§5.7).
- **Retention (OQ69).** Per-use events kept **90 days** (purge job); per-period totals per user + app + metric kept indefinitely in v1.

**Out of scope:**
- **Part C — billing / payments** (prices, paid plans, buying tokens, payment providers, invoices, tax, refunds) stays a §3 non-goal (R10). Listed in §5.7 Later only (owner, OQ57, 2026-11-18).
- Per-org pools / shared org quotas (OQ53).
- Changing token issuance: ADR-0017 §5 "issuance is never gated on entitlements" is not reopened: enforcement is the consume call (OQ66), not token issuance.

**Concept (product level, not a data model):**

| Concept | Owned by | Meaning |
|---|---|---|
| Usage metric | per app (defined by staff in v1, OQ68) | key, unit (count, seconds, …), display name |
| App default | per app + metric | free-trial limit every member gets per period |
| Reset period | per metric, initialised from the app's setting (default `weekly`; OQ64) | when used amounts start again from zero |
| User grant | per user + app + metric | raised (or lowered) per-period limit, optionally until a date, set by staff or an app admin (OQ62) |
| Usage | per user + app + metric + period | consumption reported by the app |
| Remaining | derived | effective limit − usage in the current period |

Facts PLAN must weigh:
- **Credential risk.** The existing `manifest` and `releases` keys are CI/deploy-time secrets (ADR-0016 §2–§3, ADR-0018). Per-use calls need a runtime secret in every app backend; one scope per key (ADR-0018) keeps a leaked usage key from writing manifests or releases, and vice versa.
- **Enforcement and duration metrics.** Speech-to-text duration is known only after the work is done, so "reject a usage report over the limit" cannot stop the cost already incurred; hence the consume-before-action with estimate and settle (OQ66).
- **Availability coupling.** An outage here blocks AI in every app that keeps the fail-closed default (OQ66). §6 p95 < 200 ms was set for admin reads, not per-action calls from all apps; a separate target may be needed.
- **Concurrency.** Two parallel consumes by one user must not both pass the last remaining unit (design concern for the planner/db).
- **Volume and audit.** Usage reports are high-volume and are not audit entries (one row per use would flood §5.4); staff and app-admin changes are. Usage history retention: OQ69 (90 days of events).
- **Staleness.** Limits in a token claim would be up to 12 h stale (ADR-0017); the owner chose an API call for fetching limits, so no new claim is assumed.
- **Mid-period changes.** A change to a default or grant should apply to the current period; how a period-setting change (e.g. weekly → monthly) affects the running period is a planner rule to state.
- **Join and leave.** "Default on join" can be computed for every member without a write per join; whether usage is kept when a user leaves and rejoins inside one period is a planner rule (no reset on rejoin is the safe reading).
- **Related features.** §5.12 (bug reports) and §5.13 (release log) are unrelated, except that §5.13's ADR-0018 provides the scoped-key mechanism reused here.
- **Admin UI.** admin-pan has no mock screens for this yet; UI work is in the admin-pan repo, not here.

Left to PLAN: table names, endpoint paths, final scope names (via the ADR-0018 amendment, ADM-041), rate limits, the consume latency target. Permission names are decided above (`<app>:usage:manage`, `admin:usage:read|write`).

**Out of scope for v1 (owner, 2026-11-20):** one-off credit packs, a central self-read across apps, manifest-declared metrics, user notifications of grants — all §5.7 Later.

No §3 non-goal conflict: billing stays a non-goal (OQ57); limits and usage are non-monetary counters, no prices, payments or invoices.

- [x] OQ66. What "the API enforces" means: (a) apps ask this API before each AI action, (b) this API rejects usage reports over the limit (too late for duration metrics), or (c) something else?
