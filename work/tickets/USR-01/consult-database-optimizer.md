# consult-database-optimizer — USR-01

## Findings

- **Repo baseline.** `Base.metadata` already has a naming convention (`uq_%(table_name)s_%(column_0_name)s`, `ck_%(table_name)s_%(constraint_name)s`, `ix_%(column_0_label)s`, `pk_%(table_name)s`). The only migration is `b1c724bc5edb_create_organizations` (autogenerated with `op.f()` names). `migrations/env.py` uses `compare_type=True`, no `include_object` filter. `tests/conftest.py` runs `downgrade base` → `upgrade head`, so every `downgrade()` is exercised in CI on every test session.
- **Versions (uv.lock):** SQLAlchemy 2.1.8, Alembic 1.20.1, asyncpg 0.32.0. `sqlalchemy.dialects.postgresql.CITEXT` is a first-class type, and the PG dialect reflects `citext` columns as `CITEXT`, so Alembic's type comparison matches the model → no drift.
- **citext on the shared prod Postgres:** `citext` is a **trusted extension** since PG13, so a non-superuser can `CREATE EXTENSION citext` if it has `CREATE` privilege on the current database — which database owners have. If `add-app-db.sh org_admin` makes role `org_admin` the owner of database `org_admin` (please verify), it works. The extension is per-database, so it doesn't touch other apps' databases. Locally `postgres:17-alpine` ships contrib and runs as superuser — fine.
- **Alembic vs extensions:** autogenerate neither emits nor compares extensions, so `CREATE EXTENSION` must be hand-written; `alembic check` ignores it (no drift from it).
- **Deploy model:** rollback runs the previous image on the new schema (deploy.md). A new `users` table is purely additive → safe.
- **Rate-limit runtime:** the Dockerfile runs a single uvicorn process (no `--workers`), single container deploy. An in-process limiter is exact today.

## Recommendations

1. **Email uniqueness (AC1, AC3 "409 duplicate any case"):** `email: Mapped[str] = mapped_column(CITEXT, unique=True, nullable=False)` → `uq_users_email`, and the same index serves the equality lookups for login/signup. Prefer this over a `lower(email)` functional unique index (Alembic autogenerate doesn't reliably round-trip expression indexes, and every query must remember `lower()`) and over a separate normalized column (redundant with citext). Still trim + lowercase the domain part in Pydantic. Map `IntegrityError` on `uq_users_email` to 409 (covers concurrent signups, not just the pre-check).
2. **Migration (R2, AC1):** `upgrade()`: `op.execute("CREATE EXTENSION IF NOT EXISTS citext")` then the autogenerated `create_table`. `downgrade()`: drop table, then `op.execute("DROP EXTENSION IF EXISTS citext")` — keeps `downgrade base` symmetric for conftest; comment that a later migration using citext must not drop it. `down_revision = "b1c724bc5edb"`. Hand-review; confirm `alembic check` → "No new upgrade operations detected".
3. **Columns (AC1, R9, R11):**
   - `id` UUID via `UUIDPkMixin`.
   - `password_hash`: `Text NOT NULL` (Argon2id PHC string ~97 chars, grows with salt/hash len params — don't use `String(n)`).
   - `status`: `String(20) NOT NULL server_default 'active'` + `CheckConstraint("status IN ('active', 'disabled')", name="status_valid")` → `ck_users_status_valid` (matches the organizations pattern; `StrEnum`).
   - `email_verified_at`: `DateTime(timezone=True)`, nullable, no default (unverified on signup).
   - `display_name`: `String(100)` nullable.
   - `TimestampMixin` for created/updated.
   - Optional `CheckConstraint("char_length(email) <= 254", name="email_length")` as defense-in-depth behind Pydantic validation.
4. **Staff list indexes (AC6, R9):** add **no** index beyond `uq_users_email` in this ticket. `status` has 2 values (index useless), user count is small (ecosystem accounts, not millions), ordering `created_at DESC, id` like organizations. For the email filter use case-insensitive "contains" via `User.email.contains(q, autoescape=True)` — on citext, `LIKE` is already case-insensitive; escape `%`/`_` from user input. If listing gets slow later: `pg_trgm` GIN index (also trusted → same privilege story) as a follow-up.
5. **Per-IP limiter (AC5, R7):** do **not** add a Postgres table in USR-01. Build an in-memory sliding-window/token-bucket limiter behind a `RateLimiter` protocol in `app/core/` (or a shared identity module), limits via settings (R5), injected as a dependency so tests swap it. When multiple workers/replicas arrive, swap the backend; the minimal PG design then is an UNLOGGED `rate_limit_counters (key text, window_start timestamptz, count int, PK(key, window_start))` with `INSERT … ON CONFLICT DO UPDATE SET count = count + 1 RETURNING count` plus periodic cleanup. Log as follow-up.
6. **Register model** in `app/db/models.py` (R2), otherwise `alembic check`/env won't see it.

## Risks

- **Prod privilege assumption:** if `org_admin` is not DB owner and lacks `CREATE` on the database, the deploy's `migrate` step fails (old API keeps running per deploy.md — safe failure, but blocks the release). Mitigate: confirm, or have the owner pre-create the extension once as superuser (`IF NOT EXISTS` makes the migration tolerant).
- **`DROP EXTENSION` in downgrade** fails if another object depends on citext — acceptable (detected loudly); prod never migrates down.
- **asyncpg + citext:** asyncpg decodes `citext` via its text fallback through type introspection — values come back as `str`; include one test that round-trips an email to catch surprises.
- **Status divergence:** if ADR-0001/staff later want more statuses (e.g. `pending`), changing the CHECK is a cheap additive migration — but settle `active|disabled` now.
- **In-memory limiter** resets on redeploy and is not shared across replicas — acceptable for a single container, must be revisited before scaling.
