# Security review — USR-02d

## Attempt 1 — 2026-11-11

**Verdict: no 🔴 blockers.** `make check` green (ruff, format, mypy 48 files, 348 tests). Reviewed `origin/main...HEAD` against R3, R5, R6, R9, R11, D17–D19 and ADR-0003 §9/§10.

**Checked:**
1. **TOCTOU closure.** `RbacRepository.lock_app` (`repository.py:18`) = `SELECT … FOR NO KEY UPDATE` with `populate_existing` (App re-read under the lock). Every mutation calls `_locked_app` as its first DB statement — the 7 new routes, `AppService.update`/`delete`, `build_default_role` (service.py:88, 151, 194, 229, 259, 296, 332, 352, 366, 387). All guard reads (`default_role_id`, `role_has_admin_permission`, `role_holds_permission`, `permission_held_by_any_role`, `role_has_assignments`, `is_system`, the current `role_permissions` read in `_set_role_permissions`, `permissions_by_keys`/`is_admin`) come after it. `AppService.create` only does an unlocked duplicate pre-check — the real guard is the unique index + savepoint (race → 409); `_build_for_app` works on a new row no other transaction can see — correct. `tests/test_rbac_locking.py` asserts the lock is the first SQL for all 9 HTTP mutations and `build_default_role`, and that it blocks other lockers but not `KEY SHARE`. Lock order is always one app row then child rows; FK checks take only `KEY SHARE` → no deadlock path. `role_assignments.role_id` NO ACTION → a role delete racing an assignment insert hits the FK → 409. No other code in `app/` writes `role_permissions` or `default_role_id`.
2. **Guard set** (all after the lock): prefix `split(":",1)[0] != app.key` on permission/role create (regexes require `:`); `<app>:*` forces `is_admin=true`, `false` on create/PATCH → 422 (DB CHECK second line); PATCH false→true while the default role holds it → 409; PUT of any `is_admin` permission onto the default role → 409; app PATCH `default_role_id` to a role with `is_admin` permissions → 422; `admin:super-admin` must keep `admin:*` → 409; delete `admin:*`, a permission held by any role, a system role, the default role, or a role with assignments → 409; cross-app ids/keys → 404/422 (lookups by `(app_id, id)`/`(app_id, key)`, backed by composite FKs).
3. **D19 origins** (`origins.py:37-41`): printable-ASCII check before `lower()`; label-based suffix rule. Probed and rejected: `evilmmlabs.online`, `mmlabs.online.attacker.com`, trailing dot, empty/leading-hyphen labels, `HTTPS://API.MMLABS.ONLINE`, `api.mmlabs.online:443`, `http://` on mmlabs hosts, non-default ports, `:00443`, `:080`, newline, path, userinfo, non-loopback IP literals. `xn--` accepted only under the suffix (`xn--mmlabs-online.com` rejected). Loopback http/https any port. Constant error message; handler strips `input`/`ctx` → no echo.
4. **PUT 422 `details`:** echoes only keys that already matched `PERMISSION_KEY_RE` (≤ 160 chars), ≤ 200 entries before dedupe, sorted; another app's key is reported as "unknown" (reveals nothing about other apps). Documented in the `UnprocessableError` docstring and ADR §10 — acceptable.
5. **Mass assignment:** all 6 new input models `extra="forbid"`; `key`, `is_system`, `app_id` never accepted; explicit null refused for `is_admin` and role `name`; role `name`/permission `description` refuse C0 controls and DEL.
6. **Savepoints:** `add_permission`, `add_role`, `delete_permission`, `delete_role`, `apply_role_permission_diff`, `save` run in `begin_nested()` with `IntegrityError` → `ConflictError` (409); the request session rolls back on any exception (`app/db/session.py:24`); race tests cover builder and PUT.
- **R5:** `ADMIN_RBAC_API_ENABLED` default off, refused in staging/production, requires explicit `APP_ENV` (`config.py:53,72-82`) — the right control while these privilege-changing routes are unauthenticated.

### Findings

💭 **Control-character filter misses C1 and Unicode format characters** — `app/modules/rbac/schemas.py:76`. **Risk:** role names become public via the D17 catalog (USR-02e) and appear in app UIs; still accepted: `U+0080–U+009F`, bidi overrides/isolates `U+202A–U+202E`, `U+2066–U+2069`, and `U+2028`/`U+2029` → spoofed display (e.g. reversed-rendering names) and log/line injection in consumers. Not exploitable server-side. **Fix:** extend `_NO_CONTROL` to also exclude `\x80-\x9f`, `  `, `‪-‮`, `⁦-⁩`, plus one reject test (e.g. `"a‮b"`).

💭 **App `name` has no control-character check** — `schemas.py:24`, `:40` (pre-existing, not in this diff). **Risk:** `AppCreate.name`/`AppUpdate.name` accept NUL; Postgres `text` refuses `0x00`, so likely a 500 instead of 422 (the plan names this failure mode); other controls get stored. **Fix:** same `pattern=_NO_CONTROL` on both fields (move the constant above `AppCreate`). Under R7 → follow-up or `/solo`.

💭 **Subdomains of the API host are accepted as origins** — `origins.py:39`. `https://x.api.mmlabs.online` is accepted while exact `api.mmlabs.online` is refused. `mm_device` is host-only, so no cookie impact — just a surprising entry. **Fix (optional):** also refuse `host.endswith("." + _API_HOST)`.

### Follow-ups (out of scope)
1. **Join flow (USR-03b):** assigning the default role must read `apps.default_role_id` under `FOR SHARE`/`FOR KEY SHARE` on the app row, or in one `INSERT … SELECT default_role_id FROM apps WHERE …`. Otherwise: join reads default role R; staff concurrently switch the default to R2 and PUT an `is_admin` permission onto R; the join assigns R → admin. `FOR SHARE` conflicts with this ticket's `FOR NO KEY UPDATE`, so it serializes cleanly.
2. **ADM-002 — escalation through the member role without touching the default-role invariant:** staff can clear `default_role_id`, then PUT `<app>:*` onto `<app>:member`; every existing member holds that role → all escalated. The planned "granting `is_admin`/`<app>:*` needs `admin:*`" guard covers it; also consider 409 for an `is_admin` grant on any role with assignments unless the actor holds `admin:*`.
3. **ADM-002 before removing the flag:** `admin:*` on every `# ADM-002 guard` site; consider restricting `admin:*` to `admin:super-admin` and forcing every `admin`-app permission to `is_admin`; check for `admin:`-prefixed rows created while the flag was on.
4. **USR-03 (CORS echo):** exact-string comparison of stored origins only; re-validate rows written before D19 at read time; drop loopback in staging/production (from USR-02b); keep the subdomain-takeover risk in mind for any registered `*.mmlabs.online` subdomain.
5. **USR-02e catalog:** own minimal schema (not `RoleRead`); apply the stricter character filter above before role names go public.
6. **`/solo` or small ticket:** `_NO_CONTROL` on `AppCreate.name`/`AppUpdate.name`.
