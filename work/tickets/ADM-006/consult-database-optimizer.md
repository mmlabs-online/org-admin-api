## Recommendations
Table `org_entitlements` (model in new app/modules/entitlements/, import in app/db/models.py, R2):
- id UUID pk; org_id UUID NOT NULL FK organizations.id ON DELETE CASCADE (named fk_org_entitlements_org_id_organizations); app_id UUID NOT NULL FK apps.id ON DELETE CASCADE. Note orgs and apps are never hard-deleted by the API today (check), so CASCADE is just cleanup; RESTRICT is the safer alternative for app_id if you want to block deleting an app with live grants. I lean CASCADE for org, RESTRICT for app only if apps are deletable; otherwise CASCADE for both for consistency with join_requests.
- plan VARCHAR(64) NOT NULL (free-form slug, optional CHECK on format e.g. `plan ~ '^[a-z0-9][a-z0-9_-]{0,63}$'`; avoid an enum, plans are per-product). Consider nullable if the owner wants plan-less grants; default to NOT NULL for simplicity of consumers.
- limits JSONB NOT NULL DEFAULT '{}' (server_default text("'{}'::jsonb")). Limits are per-product and free-form, so JSONB beats columns. Guards: CHECK `jsonb_typeof(limits) = 'object'` and CHECK `pg_column_size(limits) <= 4096` (or octet_length(limits::text)); validate in Pydantic too: dict[str, int|float|bool|str|None], max ~50 keys, key regex, no nesting (flat), size cap. Use plain JSONB (not none_as_null) since never NULL. Do not index limits (no query by limit).
- Enabled vs status: use `enabled BOOLEAN NOT NULL DEFAULT true` (ticket AC says "enabled" and "revoke"). Decide revoke semantics: DELETE (204, row removed; audit entry keeps history) vs soft disable. Recommend: PATCH enabled=false = disable (keeps plan/limits, reversible); DELETE = revoke = hard delete, audited (R4, R6 204). Avoid a status string; only two states are needed and suspended-org is derived from organizations.status, not stored here.
- Unique (org_id, app_id): UniqueConstraint(name="uq_org_entitlements_org_id_app_id") — convention would yield uq_org_entitlements_org_id; give an explicit name to avoid ambiguity. The composite unique index also serves "entitlements of an org" (leading org_id), so no extra index for it.
- Per-app listing: Index("ix_org_entitlements_app_id_org_id", "app_id", "org_id") (also covers the app_id FK, rule 2 of FK indexing). Active-of-org needs no partial index (few rows per org); skip `WHERE enabled` partials as premature.
- created_at/updated_at via TimestampMixin. created_by/updated_by: UUID NULL FK users.id ON DELETE SET NULL (fk_org_entitlements_created_by_users, ..._updated_by_users); staff actor id from the token. Given the audit log (R4/ADM-004) records actor+changes in the same transaction, created_by/updated_by are optional; keep only created_by if you want minimal. If kept, they need no indexes.
- Migration: new file after a9d4c27e6b13, expand-only (new table, no locks). upgrade: create_table with sa.Column("limits", postgresql.JSONB(), server_default=sa.text("'{}'::jsonb"), nullable=False), CheckConstraints via op.f("ck_org_entitlements_<name>"), explicit FK names, then create_index. downgrade: drop_index then drop_table (lossy, say so in docstring, mirroring USR-03g).
- Alembic check pitfalls: (1) server_default for JSONB must match text exactly; declare `server_default=text("'{}'::jsonb")` in both places. (2) CHECK constraints are not compared, so copy text verbatim between model and migration, and test the constraint by an insert test. (3) Import the model in app/db/models.py or autogenerate wants to drop the table. (4) Explicit names for the unique constraint and FKs; model FK names must equal migration names. (5) ON DELETE must be in both. (6) Do not use pg_column_size in a CHECK if you want portability; fine on Postgres 17 but deterministic only for stored size, so octet_length(limits::text) <= N is more predictable.
- Behaviour: "active entitlement" = enabled AND org.status='active' AND app.status='active'. Service read endpoint (R3 auth class: until ADM-002 note the permission; likely `admin:entitlements:read`, and for services see Q4/app credential class 4, which today is only for manifest PUT, so a service-read auth class needs an ADR/owner decision) returns the joined view; filter in SQL with a single JOIN (no N+1): entitlements JOIN organizations JOIN apps, select only needed columns. Suspended org: recommend reads return an empty active list (or flag org_status) while admin list still shows rows; granting/updating for a suspended org allowed for admins (or 409; pick one in the plan and test it).
- org_mode=none apps: recommend rejecting grants with 422/409 `{"field":"app","reason":"org_mode_none"}` (reuse the pattern in organizations/auth_service.py line 48). Entitlements are per org, and an app that does not use orgs cannot be consumed by org, and the `admin` app must be excluded. Counterpoint: some products may be sold per org without org-scoped roles; if so, allow. Needs owner confirmation. Also reject disabled apps on grant (404 or 409), per D17 convention that disabled/admin apps are hidden from public views.
- Endpoints (R9): /api/v1/orgs/{org_id}/entitlements (POST grant, GET list Page[T], PATCH /{app_key}, DELETE /{app_key}); address the app by key per D18 exception. Service read: GET /api/v1/orgs/{org_id}/entitlements/active (singular document, not Page) or `?active=true`; list ordering by (created_at, id) for stable paging.

## Risks
- Free-form limits JSONB without a shape contract lets consumers diverge; mitigate with flat-object guard and documenting per-app limit keys later (manifest-declared limits would be a future ticket).
- Service-to-service auth for the read endpoint is unresolved (Q4); do not invent a new credential class in this ticket (R7/R10).
- CHECK drift is invisible to `alembic check`.
- CASCADE on apps.id silently deletes grants if an app is ever hard-deleted; confirm apps are only disabled.

## Open questions

2. org_mode=none apps allowed? (Recommend reject.)
3. Suspended org: block mutations or only hide from active reads?
4. Should plan be nullable and is a plan catalog per app needed?
5. Who calls the service read: staff Bearer only for now, or a new service credential (needs ADR)?
6. Keep created_by/updated_by in addition to the audit log?
